# 현재 개발 방향: 외부 방송과 연결되는 주문 전산화

최종 갱신: 2026-09-13

## 현재 기준 (2026-09-13)

사용자가 **구현 계획과 인터페이스 작성까지** 지시했다. [방송 주문 구현 계획](plans/broadcast-orders/README.md), [화면·API 규약](plans/broadcast-orders/interfaces.md), [공동 작업표](plans/broadcast-orders/worklog.md), [모의 화면](prototypes/broadcast-orders/index.html)이 현재 기준이다. 실제 서비스 기능·결제 연동·배포는 아직 착수하지 않는다.

추가 사용자 피드백: 현장에서 사진을 찍을 시간이 없다. 현장 등록의 필수 값은 짧은 이름·가격, 번호는 자동 부여한다. 사진 없는 번호 중심 UI와 상품 수정·삭제/복구·판매 중지 규칙은 최신 구현 계획에 반영했다. 이후 고객 화면과 주문의 불일치 지적에 따라 v1.2는 접수 이력 이후 이름·가격·옵션 수정과 삭제를 잠근다. 담기만 한 초안은 변경 전후를 확인해야 접수할 수 있고, 접수 후 정정은 판매 중지와 고객의 별도 확인을 거친다.

아래 내용은 검토 과정의 기록이다. ‘최신’, ‘현재’, ‘추천 순서’라는 과거 표현이 있어도 상단의 기준 문서를 우선한다. 고객 직접 주문과 현장 상품 1회 등록이 채택된 설계 방향이며 수기/OCR 우선 후보는 배경 자료다. 개인 주문 복구 링크는 새 계획에서 **확인 후 전달하는 일회용 링크**로 구체화했다.

## 고객 직접 주문을 우선한 재검토 (2026-09-13, 최신 제안)

사용자는 손님이 직접 주문하는 것이 가장 이상적이라고 다시 강조했다. 주문 시점의 운영 선호를 물었으나 사용자는 **자신에게 선택을 묻기보다 사용자 경험 관점에서 판단해 달라**고 지시했다. 판매자 사후 정산만 개선하는 방안을 최종 목표로 축소하지 않는다. 아래의 기존 후보 순서는 작게 시작하는 개발 부담을 중심으로 정리한 것이며, 고객 직접 주문을 우선하는 최신 검토와 구분한다. 구현 금지는 유지된다.

### 위챗페이·알리페이 결제 동선 (최신 제안)

사용자는 위챗페이와 알리페이를 모두 사용한다고 추가로 알려줬다. 기존에 확인된 위챗은 아내(셀러) 명의의 개인 송금이다. 알리페이의 수취 명의·개인 계정 또는 가맹점 여부는 아직 확인되지 않았으며, 두 수단을 사용한다는 사실만으로 온라인 결제 API 이용 권한이 있다고 해석하지 않는다. 구현 금지와 사용자 경험에 따른 자율적인 제안 요청은 유지된다.

추천 고객 동선은 **방송 중 상품별 구매 요청 → 방송 후 판매자가 구매 가능 수량·상품 금액·배송비 확정 → 고객이 개인 주문서에서 합계와 통화를 확인 → 위챗페이 또는 알리페이 선택 → 입금/결제 확인 → 배송**이다. 상품마다 결제하게 하지 않고 한 방송의 확정된 요청을 모아 결제한다. 비회원 주문에 연결하며, 결제 화면으로 이동하거나 되돌아와도 해당 주문으로 돌아갈 수 있게 설계한다.

| 단계 | 동작 | 완료 판단 |
| --- | --- | --- |
| 초기 주문 동선 시험 | 기존에 실제 사용하는 수금 경로의 금액·수취인·송금 안내 제공 | 수취 계정에서 실제 입금을 확인한 권한자가 확정 |
| 정식 온라인 결제 연동 | 계약된 PG 결제창에서 위챗페이·알리페이 결제 | PG의 검증된 결제 결과로 주문에 반영 |

초기에는 ‘위챗페이 송금 안내’, ‘알리페이 송금 안내’처럼 실제 기능에 맞게 표시한다. 금액·주문번호 복사와 해당 수금 경로 안내를 제공한다. 사용자는 ‘송금했어요’를 누르려면 증거가 있어야 한다고 지적했으므로, 단순 자기 신고에서 **송금내역 첨부 → 입금 확인 요청** 동선으로 계획을 보완한다. 알리페이가 개인 송금이라면 같은 원칙을 적용하고 상점 계정이라면 해당 계약과 API 범위를 따로 확인한다.

일반 제출 경로에는 해당 거래의 송금완료 또는 거래 상세 화면 캡처를 최소 1장 첨부하도록 제안한다. 화면에 금액·통화, 받는 사람, 송금 시각, 처리 상태가 보이도록 안내하며 거래번호가 표시되는 경우 함께 확보한다. 관계없는 잔액·다른 거래 내역을 요구하지 않는다. 해당 개인 주문에서 제출하므로 주문번호·고객·선택 결제수단은 자동 연결하고, 화면에서 확인되지 않는 대조 정보만 추가 입력받는다. 업로드와 주문 연결 저장이 성공한 뒤 ‘입금 확인 요청’을 제출할 수 있게 하며, 첨부 중이거나 실패했을 때 접수 완료로 표시하지 않는다.

고객 상태는 **결제 대기 → 입금 확인 대기 → 입금 확인 완료**로 구분한다. 캡처는 대조 자료이며 조작·재사용·수취 미완료 가능성이 있어 파일 첨부만으로 실제 입금을 확정하지 않는다. 실제 수취 계정의 거래 내역과 금액·상대방·시각·수취 상태 등을 확인한 권한자가 완료 처리한다. 같은 금액만으로 자동 매칭하지 않고 거래 중복 사용·부족 송금·초과 송금을 확인한다. 대조가 안 되면 추가 확인 상태로 두며 원본 증빙과 수정·재제출 이력을 보존한다. 고객 본인과 해당 주문의 확인 권한자만 증빙을 열람하게 한다.

사진을 첨부할 수 없는 고객을 위한 보조 경로로 거래번호와 송금자·금액·시각 등의 정보를 제출해 담당자 확인을 요청하는 안을 둔다. 이 경로 역시 실제 수취 내역 대조 전에는 완료하지 않는다. 거래번호가 양쪽 앱에서 같은 형식으로 보인다고 가정하지 않는다. 인식 기능을 추가하더라도 금액·날짜 등 입력 보조로 사용하며 사진의 진위나 입금 완료를 AI가 보증한다고 안내하지 않는다. 이번 보완은 계획이며 구현·실거래 검증은 하지 않았다.

모바일에서는 **휴대폰 한 대로 결제하고 주문서로 돌아오는 동선**을 선정 기준으로 삼는다. QR 이미지를 보여 준다는 사실만으로 앱 호출·금액 자동 입력·원격 결제·결과 통지가 된다고 가정하지 않는다. 개인 수금 QR의 사진 저장·앨범 인식이 모든 환경에서 가능하다고 안내하지 않으며, 이미 사용 가능한 송금 경로 또는 계약된 모바일 결제 수단을 기준으로 검증한다.

목표는 두 수단의 정식 결제 연동과 사용자가 원하는 플랫폼 수금·셀러 정산의 연결이다. KG이니시스는 공식적으로 위챗페이·알리페이를 글로벌 결제로 제공하고 별도 신청·심사·연동 절차를 안내한다. 수수료는 별도 협의다. 이 서비스의 존재가 오렌담마켓의 입점이나 중국 주소 배송·제3자 셀러 수금 및 정산·모바일 결제 동작까지 승인됐다는 뜻은 아니다. [공식 결제수단](https://www.inicis.com/pg-method), [글로벌 결제 신청·심사](https://inicis-service.inicis.com/?page_id=747). 실제 현장 판매 구조에 대한 업종·계약 적합성과 휴대폰 결제 동작을 확인한 뒤 토스 유지·병행·교체를 판단한다. [입점 조건](https://www.inicis.com/service-application).

초기 송금이 아내 계정으로 들어가면 **셀러 직접 수금**으로 기록한다. 플랫폼이 받은 판매대금 또는 셀러에게 다시 지급할 금액으로 처리하지 않는다. 알리페이도 확인된 실제 수취인을 기준으로 분류한다. 계약된 플랫폼 수금으로 전환한 거래만 해당 수금·정산 경로로 처리하고, PG 결제 승인·플랫폼 정산 입금·셀러 지급 완료를 구분한다. 개인 송금을 영구 운영 모델로 확정하지 않는다. 이번에는 공개 자료와 계획만 갱신했으며 결제대행사 문의·가입·계정 연결·실거래는 하지 않았다.

### 공용 링크 사전 공유와 비회원 주문 구분 (최신 제안)

사용자는 상품 묶음 주문 제안에 긍정적으로 반응하고 더우인 채팅의 링크 마스킹 가능성을 우려했다. 방송 전 공유와 공용 링크 하나로 고객별 주문을 구분하는 방법을 질문했다. 마스킹 동작은 실제 시험하지 않았고, 질문은 구현 착수나 모든 운영 조건의 승인으로 해석하지 않는다.

추천은 **셀러별 고정 공용 링크를 방송 전에 기존 고객 연락 경로로 전달 → 사용할 일반 브라우저에서 한 번 열어 두고 즐겨찾기 → 방송 중 같은 링크로 들어와 자신의 장바구니에 담기 → 방송 후 개인 주문 확인·배송지·결제 안내**다. 기존에 위챗 그룹·개별 연락 등 외부 연락 경로가 있다면 우선 활용한다. 더우인 채팅의 전송 시점만 앞당기면 링크 제한이 풀린다고 가정하지 않는다. 마스킹을 우회하는 링크 변형을 제안하지 않는다.

| 구분 | 역할 | 공유 범위 |
| --- | --- | --- |
| 셀러 공용 링크 | 현재 방송 상품 목록과 주문 진입 | 여러 고객에게 동일하게 공유 |
| 비회원 장바구니·주문 | 브라우저의 비회원 접근 자격에 연결한 고객별 내용 | 서버가 각 요청의 접근 범위를 확인 |
| 개인 주문 확인·복구 링크 | 다른 브라우저나 기기에서도 해당 주문을 다시 찾기 | 본인에게만 전달·저장 안내 |

첫 방문에 서버가 추측하기 어려운 비회원 자격을 발급하고 브라우저에 보관하게 한다. 주문은 서버에 저장하며 해당 자격이 허용한 주문만 조회·변경한다. 비회원 자격은 공용 링크에 넣지 않는다. 쿠키·세션으로 장바구니 상태를 구분하는 웹 설계를 활용하는 것이며 손님 기기 고유번호·IP·닉네임으로 동일인을 자동 판별하는 방식이 아니다. [쿠키와 장바구니 상태](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies), [세션 접근 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

고객은 가입 없이 둘러보고, 첫 구매 요청을 확정할 때 판매자가 알아볼 방송 닉네임 등의 표시 정보와 연락 가능한 수단을 최소 입력하도록 제안한다. 기존에 확인된 개인 링크로 진입한 고객은 해당 연결을 활용할 수 있다. 입력한 닉네임·연락처만으로 본인 인증이나 과거 주문 연결을 하지 않는다. 같은 별명의 고객은 다른 주문으로 유지하며 위챗에서 공용 링크를 눌렀다고 위챗 ID를 자동 수신하지 않는다.

같은 브라우저에서 비회원 자격이 유효한 동안에는 주문을 이어갈 수 있게 한다. 위챗 내 브라우저와 일반 브라우저 사이의 이동, 기기 변경, 시크릿 모드, 저장 정보 삭제·만료에서는 유지되지 않을 수 있다. 처음부터 사용할 브라우저를 정해 두고 첫 요청 저장 후 ‘내 주문 다시 열기’ 개인 링크를 저장하는 동선을 함께 둔다. 링크에는 주문 범위·유효기간·재발급 관리를 두며 단체방에 공유하지 않는다. 분실 때는 확인된 기존 연락 경로 등으로 본인 연결을 확인한 뒤 재발급하며, 닉네임이나 주문번호만으로 접근을 허용하지 않는다. 중국 SMS나 위챗 로그인 연동을 이미 확보했다고 가정하지 않는다. 전체 주소·연락처 노출과 중요 정보 변경에는 필요한 확인을 더한다.

고정 공용 주소를 다음 방송에도 재사용할 수 있지만 주문은 선택한 셀러·방송 회차에 고정한다. 새 방송이 시작돼도 이전 요청을 새 회차로 옮기지 않는다. 같은 브라우저를 여러 사람이 공유할 때에는 손님 전환 동선이 필요하다. 현재 쇼핑몰의 로그인·상품·재고 검증을 전역으로 완화해서 연결하지 않는다.

이 사전 공유안은 기존 고객의 진입을 돕지만 방송 중 처음 들어온 고객에게 주소를 전달하는 문제는 별도로 남는다. 해당 더우인 계정에서 허용되고 실제 이용 가능한 연결 경로를 확인해야 한다. 중국에서 VPN 없이 링크 열기·주문 저장·재접속·개인 주문 복구는 구현 후 검증 대상이다. 이번에는 계획만 갱신했으며 고객에게 링크를 보내거나 기능을 구현하지 않았다.

### 현재 조건에서 추천하는 제품 동선: 상품 묶음 소개 후 짧은 주문 시간

방송 중 상품 몇 개를 소개한 뒤 새 상품 설명을 잠시 멈추고 고객이 오렌담마켓에서 직접 고르는 시간을 둔다. 초기 시험 예시는 3~5개 상품과 60~90초 주문 구간이다. 검증된 최적 간격이나 접속·주문 완료 시간 보장이 아니며, 실제 방송과 중국 고객 기기에서 조정할 가정이다. 주문 페이지는 그 시간이 끝나도 기존 상품을 찾을 수 있게 하며, 기한을 둘 때는 실제 확보 조건에 맞춰 명확히 안내한다.

1. 방송 회차에는 처음부터 상품 목록이 있을 필요가 없다. 보조 담당자가 현장에서 상품 사진 또는 알아보기 쉬운 방송 화면, 짧은 식별 정보·가격을 상품당 한 번 남긴다. 옵션이 정해지는 대로 표시하며, 상품 등록에 드는 실제 시간도 시험한다.
2. 고객은 묶음 소개 중 방송을 시청한다. 주문 시간에는 상품 사진 목록에서 색상·수량을 선택하거나 필요한 옵션을 입력하고 구매 요청을 저장한다. 모든 고객이 각자 입력하므로 담당자가 20건을 차례로 타이핑하지 않는다.
3. 주문 시간에는 새 상품을 소개하지 않으므로 고객이 앱을 전환한 동안 상품 설명을 놓칠 부담을 줄일 수 있다. 고객은 저장 확인 뒤 더우인으로 돌아간다. 외부 주문 페이지에서 더우인 영상·소리가 계속 재생되거나 자동 복귀한다고 약속하지 않는다.
4. 회원가입을 강제하지 않고 손님 구분에 필요한 최소 정보 또는 기존 고객별 링크를 이용한다. 저장된 상품과 옵션을 고객이 확인할 수 있게 하며, 배송지·최종 금액 확인·결제는 회차별로 모아 처리하는 방향이다. 구매 가능 수량과 가격이 확정되지 않은 요청을 확정 판매로 취급하지 않는다.

예상 장점은 고객 직접 입력, 사진으로 상품 재확인, 고객별 주문 내용 확인, 담당자 주문 타이핑 감소다. 실제 전환율 향상이나 방송 시간 단축을 검증한 것은 아니다. 새로운 부담은 상품당 정보 등록, 방송 중 주문 시간, 앱 이동과 복귀다. 방송 종료 후 3~4시간의 상품을 모두 기억해 다시 고르는 방식은 주 경로보다 추가 구매·누락 보완용으로 두는 편이 낫다는 사용자 경험상 판단이다.

외부 주문 링크를 더우인 방송·프로필·메시지에서 안내할 수 있는지는 해당 계정과 판매 용도의 정책에 따라 확인해야 하며, 플랫폼 제한을 우회하는 안내 방식을 설계하지 않는다. 현재 정산서를 전달하는 고객 연락 경로를 활용할 수 있는지도 검토한다. 중국 고객이 VPN 없이 페이지를 열고 저장할 수 있는 품질은 별도 시험 대상이다. 채팅 주문과 웹 구매 요청을 중복 확정하지 않도록 전환 기간의 접수 기준을 명확히 해야 한다.

### 시청 중 직접 주문의 더 자연스러운 후보: 더우인 자체 상점

앞서 검토한 자체 미니프로그램과 별개로 **더우인 자체 상품·장바구니·주문 기능(抖店)**을 사용하고 오렌담마켓이 허용된 주문 관리 정보를 연결받는 경로도 검토한다. 고객이 이미 있는 앱에서 상품을 선택할 수 있다는 점에서 사용자 경험상 가장 자연스러운 후보라는 판단이다. 모든 기기의 주문·결제 과정 내내 영상이 계속 재생된다는 실기기 검증은 없다.

공식 상점 개방 플랫폼은 판매자용 상품·재고·주문 관리 API를 제공한다. 이것은 임의의 라이브 채팅을 수집하는 권한과 별개이며 상점·앱의 등록 및 이용 권한을 확인해야 한다. [공식 상점 API 안내](https://op.jinritemai.com/). 더우인 공식 사례에서도 방송 내 상품 담기와 주문 동선을 설명한다. [공식 운영 사례](https://school.jinritemai.com/doudian/wap/article/aHb9JVFDfxGE?from=longpic_B&from_school=1&should_full_screen=1&should_hide_bottom_nav=1).

다만 현재 확인된 한국 사업자등록만으로 글로벌구매 상점에 즉시 입점할 수 있다고 보지 않는다. 2026-07-14 갱신된 공식 글로벌구매 입점 규칙은 해외 등록 회사·해외 소매 또는 무역 자격, 중국 본토 내 연대책임을 지는 대리인, 해외 사업용 은행 계좌 등을 요구한다. 사용자는 중국 현지 협력자가 없다고 답했다. 현장 상품의 정보·증빙 준비와 게시 절차가 방송 속도에 맞는지도 미확인이다. [공식 글로벌구매 입점 규칙](https://school.jinritemai.com/doudian/wap/article/108056?from=douyinoffici&from_school=1&should_full_screen=1&should_hide_bottom_nav=1).

이 경로의 주문·결제는 더우인 상점의 거래 체계를 따른다. 오렌담마켓으로 주문 관리 정보를 연결할 가능성과 기존 플랫폼 수금·셀러 정산 방식을 그대로 유지할 수 있는지는 별개다. 해외 사업자·상품 공급·국제배송 조건이 충족되기 전에는 도입 확정이나 등록·결제 테스트를 진행하지 않는다. 단, 제품 계획과 공개 자료 검토는 계속 가능하다.

따라서 고객 직접 주문이라는 기준에서는 오렌담마켓의 상품 묶음 주문 동선을 구체화하고, 더우인 자체 상점의 이용 가능성은 별도 검토하는 방향을 추천한다. 두 방식 중 어느 것도 사용자가 채택했다고 기록하지 않는다. 고객이 방송을 끊김 없이 계속 보면서 주문해야 한다는 추가 조건이 확정된다면 외부 페이지의 짧은 주문 구간이 그 조건을 충족한다고 주장하지 않는다.

## 앞선 후보 추천 순서 (2026-09-13, 작게 시작하는 개발 기준)

사용자는 지금까지 나온 방법을 추천 순으로 정리해 달라고 요청했다. 방송을 지연시키지 않고 실제 정리 업무를 줄일 가능성, 고객의 추가 행동, 이용 자격의 불확실성을 기준으로 비교한다. 이는 사용자가 채택한 결정이 아니다.

| 순위 | 방법 | 현재 판단 |
| --- | --- | --- |
| 1 | 현재 수기 기록을 바탕으로 방송 후 주문·정산 전산화 | 제품 개발의 우선 후보. 한 번 입력한 주문을 고객별 분류·합계·정산서에 재사용한다. 원본에서 옮기는 작업과 확인은 남고 방송 중 수기 부담은 줄지 않는다. 수기 사진 인식은 별도 표본 검증 후보다. |
| 2 | PC 녹화에서 채팅을 추출해 주문 초안 생성·검수 | 입력 자동화의 우선 시험 후보. 1번의 입력 부담을 줄이는 단계이며 원본 누락·고객 식별·상품 연결·검수 시간 검증이 필요하다. |
| 3 | 보조 담당자가 방송 중 전자 주문장 입력 | 고객별 타이핑을 기다릴 수 없다는 현장 피드백으로 보류한다. 기술 구현 가능성과 현재 운영 적합성을 구분한다. |
| 4 | 고객이 방송 중 별도 웹·앱에서 직접 주문 | 모바일에서 방송과 주문 화면을 함께 쓰기 어렵다는 제약으로 보류한다. 방송 후 주문 확인용 웹은 별개로 추천한다. |
| 5 | 안드로이드 앱을 더우인 위에 표시 | 설치·표시 권한·기기 검증 부담이 있고 아이폰까지 공통 제공할 경로가 확인되지 않아 후순위다. |
| 6 | 더우인 미니프로그램 안에서 주문 | 판매용 라이브 연결·주문·결제 조건을 먼저 충족해야 하므로 현재 개발 착수 후보로 삼지 않는다. |
| 7 | 오렌담마켓 자체 라이브와 주문 통합 | 영상 운영과 중국 접속 문제, 고객 이동 부담이 추가되므로 주문 업무 개선 뒤의 장기 후보로 둔다. 국내부터 방송하는 선택지는 유지한다. |

실제로 먼저 추진할 것을 추천하는 범위는 1·2번이다. 3번 이하의 순위가 현재 도입을 권한다는 뜻은 아니다. 1번에서 방송 후 검토·정산의 공통 경로를 마련하고, 2번 표본 시험이 유효할 때 그 경로의 입력을 자동화하는 순서다. 어느 입력 방식이든 고객별 비회원 주문 확인·배송지·수금 안내로 이어가는 목표를 유지한다.

**공식 채팅 원본 연동은 조건부 후보로 별도 취급한다.** 필요한 댓글·고객 ID를 적합한 사용 권한과 판매·외부 주문 관리 용도 아래 확보할 수 있다면 녹화 OCR보다 먼저 비교할 가치가 있다. 그러나 공개 상호작용 도구 접속 안내는 신규 플러그인 접수 중단을 명시하며 현재 계정에서 쓸 수 있는 경로는 미확인이다. 따라서 사용할 수 있다고 전제해 개발 순위를 올리지 않는다. [공식 접속 안내](https://developer.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/introduction/interactive-tools-guide). 미니프로그램 역시 판매용 라이브 연결이 일부 초청 사례 외 비개방이고 주문·결제는 抖店 기능을 사용한다는 조건이 있다. [공식 판매용 기능 범위](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/Industry/online-retailers/capacity-inventory).

## 최신 현장 피드백과 수정안 (2026-09-13)

**녹화 추출 검토의 추가 확인:** 방송은 한 회 3~4시간이고 PC·휴대폰 화면 녹화 모두 가능하며, 주문 채팅은 한국어가 대부분이다. 실제 녹화본은 아직 시험하지 않았다. 인식률·개발 난이도·비용·내보내기 시간의 근거와 조건부 계산은 [녹화본 주문 추출 검토](research/2026-09-13-douyin-recording-order-extraction.md)에 정리했다. 공개 OCR 모델 성능을 실제 주문 정확도로 보지 않으며, 예상 시간에는 전송·연산·사람의 검수를 구분한다.

사용자는 아내와 논의한 결과 상품 하나에 주문이 최대 20건 들어오며, **보조 담당자가 주문을 타이핑할 때까지 방송 진행을 기다리기 어렵다**고 확인했다. 또한 **주문 수량은 방송 후 취합해도 된다**고 답했다. 따라서 이전의 방송 중 고객별 전자 주문장 입력을 주 경로로 하는 제안은 보류한다. 사용자는 더우인 라이브에서 PIP가 안 되는 것 같다고 보고했다. 모든 기기·버전의 지원 여부를 단정하지 않되, 계획은 PIP 없이도 성립해야 한다.

수정 추천안은 **더우인 채팅 주문 → 원본 주문 기록 보존 → 방송 후 주문 초안 작성·담당자 확인 → 고객별 정산서 → 비회원 주문 확인·결제 안내**다. 방송 중 20건을 모두 타이핑하는 작업을 상품 전환의 조건으로 두지 않는다. 고객이 시청 중 오렌담마켓으로 이동할 필요도 없다. 방송 후 취합 가능하다는 답이 재고 무제한이나 모든 요청의 구매 가능 확정을 뜻하지는 않으므로 확보 수량은 청구 전에 확인한다.

전산화할 입력 자료는 다음 순서로 검증하며 아직 채택하지 않았다.

1. **채팅 원본을 확보하는 경로:** 판매자 계정에서 이용 가능한 기록·내보내기 기능이나 채팅 화면을 보존하는 방법이 있는지 확인한다. 화면 녹화를 후보로 검토할 수 있지만 실제 파일에 고객 식별 정보와 모든 주문이 남는지 검증 전이다. 방송 다시보기에 당시 채팅이 전부 포함된다고 가정하지 않는다. 공식 공개 댓글 상호작용 문서도 특정 라이브 놀이의 지시어 메시지를 대상으로 하므로 일반 판매 채팅 전체의 수집 권한이나 내보내기를 증명하지 않는다. [공식 댓글 상호작용 범위](https://partner.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/hudongshuju/pinglunshuju).
2. **현재 수기 기록을 방송 후 전산화:** 현재 손으로 적는 방식이 현장 속도를 따라간다면 그 기록을 촬영해 문자 인식·AI로 주문 초안을 만드는 안을 검토한다. 현장 기록은 남지만 고객별 재분류·계산·정산서 재작성 부담을 줄이는 목적이다. 수기 인식의 정확도와 확인에 드는 시간은 실제 표본으로 평가해야 한다.

채팅 기록을 활용할 때는 상품 전환을 짧은 메모·번호·시각 등으로 식별할 수 있어야 한다. 정확한 방법과 작업량은 미정이다. 상품 전환 시각만으로 늦게 도착한 주문을 자동 확정하지 않으며 상품명·가격은 방송 후 보완할 수 있다. 고객 ID, 색상·수량, 중복 댓글, 수량 변경·취소, 상품 경계가 모호한 요청은 원본과 연결해 담당자가 확인한다. 화면에 표시되지 않았거나 저장되지 않은 주문을 AI가 복구한다고 약속하지 않는다. 인식 결과는 청구 가능한 확정 주문이 아니라 초안이다.

첫 검증은 실제 상품 한 개에서 주문이 몰리는 구간을 대상으로 **기록 누락, 잘못된 고객·상품 연결, 중복·취소 처리, 인식 후 수정 시간, 방송 중 추가 대기 발생 여부**를 현재 수기 기록과 비교하는 것이다. 신뢰할 수 있는 원본 확보와 확인 부담 감소가 검증되기 전에는 수기 기록을 없애거나 자동 청구·자동 발송으로 진행하지 않는다. 이번에 합의된 것은 현장 제약과 방송 후 취합 가능 여부이며, 녹화·AI 인식 방법의 채택이나 구현은 승인된 것이 아니다.

## 사용자가 정한 우선순위

핵심 목적은 현재 수동으로 처리하는 주문 업무의 전산화·자동화다. 고객이 다른 플랫폼에서 방송을 보더라도 오렌담마켓 웹이나 앱에서 상품을 주문할 수 있어야 한다.

- 자체 라이브 스트리밍은 주문 시스템의 필수 조건이 아니다.
- 중국 라이브는 후순위로 둔다. 자체 방송을 도입한다면 우선 국내만 제공해도 된다.
- 중국 고객은 주요 도시가 연길로 추정되며, VPN 없이 일반 브라우저에서 주문할 수 있는 경로를 우선 검증한다.
- 배우자가 셀러로 실제 업무에 사용할 예정이다. 한국 사업자등록이 있고, 중국 현지 사업자·협력업체는 없다.
- 현재 방송 플랫폼은 **중국판 틱톡인 더우인(抖音)**이다.
- **모바일에서 방송과 오렌담마켓을 함께 열기 어렵다.** 방송 중 고객에게 별도 앱·브라우저로 반복 전환하도록 요구하는 기존 제안은 재검토한다. 고객이 시청을 계속하면서 주문할 수 있는 동선이 먼저다.
- 방송 플랫폼과의 직접 API 연동 없이도 판매자의 기록·취합·정산을 전산화할 수 있다. 다만 고객 입력까지 자동 연결하려면 더우인의 실제 연동 가능 범위 확인이 필요하다. 외부 주문 링크는 방송 후 확인·정산·배송지 입력 경로로도 검토한다.
- **상품 사전 등록은 불가능하다.** 방송 때마다 다른 매장을 방문하고, 현장에 도착해야 어떤 상품이 있는지 알 수 있다. 상품 목록·옵션·가격·재고를 미리 갖춰야만 주문받을 수 있는 구조를 요구하지 않는다.
- 고객이 오렌담마켓에서 자신의 주문장을 확인하고 결제까지 이어가게 하는 동선을 원한다. **회원가입을 강제할 수 없으며, 고객이 체감할 편의가 있어야 가입할 것**이라는 점을 사용자가 강조했다. 비회원 정산서와 선택 가입 흐름을 제안 단계로 검토한다.
- 기존 오렌담마켓은 **고객이 플랫폼 운영자 계좌로 입금하고 운영자가 셀러에게 정산하는 중개 모델**이다. 사용자는 방송 주문도 이 모델과 결합할 수 있는지 검토를 요청했다. 현재 중국 방송 수금 명의와의 차이는 아래 별도 항목을 따른다.

이 문서의 우선순위가 앞선 [중국 라이브 검토 기록](reviews/2026-09-12-china-live-streaming.md)의 영상망 선정 순서보다 우선한다.

## 확인된 현재 업무

사용자가 설명한 실제 절차:

1. 더우인 방송으로 상품을 안내한다.
2. 고객은 **현재 소개 중인 상품**을 가리켜 채팅에 “2개”, “빨간색으로 한 개”처럼 수량·옵션을 남긴다. 상품 번호를 사용하는 방식이 아니다.
3. 주문이 들어올 때마다 **손님 ID와 함께 수기로 기록**한다.
4. 방송이 끝난 뒤 기록한 주문을 고객별로 정리하고 금액을 계산한다.
5. 각 고객에게 정산서를 보낸다.
6. 입금을 확인한다.

중국 고객의 배송지는 **중국 내 고객 본인 주소**이며, 결제는 **중국 계좌 또는 위챗페이**로 받는다. 사용자가 위챗페이는 **개인 계정 송금**이고, 중국 계좌·위챗 계정의 명의는 **아내(셀러)**라고 확인했다. 현재 중국 방송 수금을 플랫폼 운영자의 수금으로 기록하지 않는다. 상점용 결제 계정이나 온라인 결제 권한이 있다고 가정하지 않는다.

2026-09-13 추가 정보: 위챗페이와 **알리페이도 모두 사용**한다고 알려줬다. 알리페이의 계정 유형·수취 명의·온라인 결제 연동 권한은 미확인이다.

방송을 도와주는 **별도 담당자가 있고 휴대폰이나 PC를 사용할 수 있다.** 2026-09-13에는 상품 하나당 최대 20건을 담당자가 타이핑하는 동안 방송이 기다리기 어렵다고 확인됐다. 주문 취합은 방송 후 가능하므로 실시간 전산 입력을 필수로 두지 않는다.

따라서 가장 먼저 줄일 작업은 방송 후 고객별 주문 취합·합계 계산·정산서 작성이다. 이 문서의 고객 정산서는 고객에게 결제할 금액을 안내하는 문서이며, 기존 `seller_settlements`의 셀러 수수료·지급 정산과 구분한다.

## 기존 중개 모델과 방송 주문의 수금·정산 결합 (추천안)

**확인된 사실:** 기존 오렌담마켓은 플랫폼 운영자가 먼저 수금하고 셀러에게 정산한다. 현재 중국 방송은 아내 명의의 중국 계좌·위챗 개인 계정으로 수금한다. 두 흐름의 실제 돈을 받는 주체가 다르다. 고객의 회원가입 여부는 이러한 정산 구분과 별개다.

**기능 구성 제안:** 일반 쇼핑몰 주문과 방송 주문은 접수 과정을 구분하되, 금액이 확정된 주문·고객 청구·실제 수금·셀러별 정산 내역을 오렌담마켓에서 함께 관리한다. 각 주문에는 셀러와 실제 수금 주체·수단·통화를 명시한다. 고객 전용 링크에서도 실제 수취인을 정확히 안내한다.

| 수금 방식 | 실제 자금 흐름 | 정산 처리 제안 |
| --- | --- | --- |
| 플랫폼 수금 | 고객 → 플랫폼 수금 수단 → 셀러 | 실제 입금과 정산 조건 확인 후 판매액에서 약정 수수료·취소·환불·기지급액 등을 반영해 셀러 지급액 산정 |
| 셀러 직접 수금 | 고객 → 셀러 수금 수단 | 셀러가 이미 받은 판매대금을 플랫폼의 셀러 지급액으로 다시 잡지 않음. 중개 수수료를 적용한다면 약정에 따라 셀러가 플랫폼에 낼 수수료를 별도 산정 |

예를 들어 동일 통화의 상품대금 100, 약정 수수료 10, 다른 공제·환불이 없는 경우 플랫폼 수금이면 셀러에게 지급할 금액은 90이다. 셀러 직접 수금이면 판매대금은 이미 셀러에게 있으므로 플랫폼이 다시 지급할 금액은 없고 셀러에게 받을 수수료가 10이다. 실제 수수료율·배송비 처리·정산 시점은 별도로 결정한다.

사용자가 원하는 **플랫폼 수금 후 셀러 정산으로 완전히 일원화**하려면 중국 고객이 실제로 플랫폼이 수취할 수 있는 적합한 결제 경로로 지불해야 한다. 셀러 명의로 받은 대금을 화면 표시만 바꿔 플랫폼 수금으로 취급할 수 없다. 해당 수취 경로를 확보하기 전에는 아내의 직접 수금 주문을 별도 방식으로 관리하는 안을 검토할 수 있다. 이는 선택지이며 수금처 변경이나 직접 수금 모델 채택을 사용자가 승인한 것은 아니다.

공통 정산 관리에 필요한 구분:

- **주문 금액 확정 → 입금 확인 → 정산 가능 → 지급 완료**를 구분한다. 고객의 송금 신고는 실제 입금 확인이 아니다. 입금만으로 즉시 셀러 지급이 가능하다고 가정하지 않으며, 지급 시점과 취소·환불 반영 규칙은 약정에 따른다.
- 보조 담당자는 주문 기록을 맡는다. 플랫폼 수금의 입금 확정과 셀러 지급 확정은 플랫폼 관리자 또는 별도로 부여된 권한이 필요하다. 아내 명의의 수금 확인은 셀러 수금 확인으로 기록하며 플랫폼 계좌 입금 확인과 구분한다.
- 같은 거래를 일반 주문과 방송 주문 양쪽에서 중복 집계하지 않도록 원본 주문과 수금·지급 내역의 연결을 유지한다. 부분 취소·환불은 해당 상품의 수수료와 정산 금액에도 반영한다.
- 위안과 원화는 합산하지 않는다. 수금 통화·정산 통화가 다르면 적용 환율·기준 시점·비용 부담·실제 환전액을 확인해 기록한다. 셀러에게 줄 돈과 받을 수수료는 구분하고, 자동 상계는 합의된 규칙 없이 적용하지 않는다.
- 현재 `seller_settlements`는 결제된 주문의 판매액에서 수수료를 뺀 셀러 지급액을 계산하며, `seller_payouts`는 셀러에게 지급한 금액을 기록한다. 방송 주문을 여기에 단순 추가하면 셀러 직접 수금과 통화 차이를 반영할 수 없다. 공통 정산 관리로 확장할 때 실제 수금 주체·통화·정산 가능 상태와 수수료 미수 내역을 반영해야 한다. 기존 `create_order`의 등록 상품·구매자 로그인·재고 검증을 완화해서 연결하는 방식은 피한다.

플랫폼의 제3자 판매대금 수취·정산은 실제 수금 구조에 따른 제도 검토도 필요하다. 금융위원회는 전자적 결제대금 정산에 관여하는 중개업의 PG 등록과 외부 PG가 정산을 대행하는 경우를 구분해 안내한다. 이번 계획으로 해당 모델의 적법성이나 한국·중국 간 수금·정산 허용 여부를 확정하지 않는다. 운영 적용 전에 실제 수취 주체와 거래 구조를 기준으로 결제 사업자·전문가와 확인할 항목이다. [금융위원회 공식 설명](https://www.fsc.go.kr/no010102/82523).

### 한국 사업자로 중국 고객의 온라인 결제를 받는 경로 (2026-09-12 확인)

한국 사업자이고 중국 현지 법인이 없다는 이유만으로 위챗페이 수금이 불가능한 것은 아니다. 기존 아내의 개인 계정 송금과 국내 PG를 통한 해외 가맹점 결제는 별도 경로다. 다음은 공개 서비스의 존재를 확인한 것이며 오렌담마켓의 입점 승인이나 계약 체결을 뜻하지 않는다.

- **KG이니시스:** 현재 공식 결제수단 안내에 해외 판매 가맹점용 위챗페이·알리페이와 별도 신청을 명시한다. 공식 글로벌 결제 소개서는 현지 법인 없이 국내에서 해외 고객에게 판매할 수 있고, 가맹점의 승인·정산 통화를 KRW 또는 USD 중 선택할 수 있다고 설명한다. 실제 적용 조건·환율·수수료는 신규 계약 기준으로 확인한다. [현재 결제수단 안내](https://www.inicis.com/pg-method), [공식 소개서](https://inicis-service.inicis.com/wp-content/uploads/2023/download/global-payment/%5BKG%EC%9D%B4%EB%8B%88%EC%8B%9C%EC%8A%A4%5DGlobal_brochure.pdf).
- **엑심베이:** 공식 온라인 결제 안내에 중국 결제수단 WeChat과 국내 개인·법인 사업자의 신청 서류 및 사이트 심사 절차가 있다. 다만 같은 안내에서 구매대행을 금지업종으로, 소셜커머스를 협의 대상 업종으로 분류하므로 현장 판매·중개 구조를 설명하고 해당 여부를 확인해야 한다. 오렌담마켓이 이 업종에 해당한다고 확정하거나, 반대로 자동 승인된다고 가정하지 않는다. [온라인 결제·신청·업종 조건](https://www.eximbay.com/info-online.do).
- **토스:** 토스페이는 고객이 사용하는 간편결제이고 토스페이먼츠는 온라인 결제대행 서비스다. 토스페이먼츠의 공개 안내에 해외 결제와 중국·동남아 간편결제가 있지만 이번 확인에서 위챗페이의 구체적인 지원·신규 계약 조건은 확인하지 못했다. 미지원으로 단정하지도, 기존 토스 연동으로 위챗까지 활성화된다고 가정하지도 않는다. [토스 서비스 구분](https://pay.toss.im/), [토스페이먼츠 결제창 안내](https://docs.tosspayments.com/resources/glossary/payment-window).

검토할 목표는 **비회원 고객의 주문서 확인 → 위챗페이 상점 결제 → 검증된 결제 결과로 주문에 반영 → 계약된 방식으로 플랫폼 수수료·셀러 정산 처리**다. PG 입금 전 결제 승인과 실제 정산금 입금은 구분한다. 개인 송금 확인은 기존 수동 방식으로 남길 수 있으며 상점 결제와 혼동하지 않는다.

우선 확인할 계약 조건은 (1) 중국 본토 고객이 중국 주소로 받는 실제 상품 거래와 공급·출고 국가, (2) 플랫폼이 다른 셀러의 판매대금을 수취하고 수수료를 공제하는 구조의 승인, (3) 계약상 판매자·환불 책임자와 셀러 등록 요건, (4) 고객 결제 통화와 플랫폼·셀러 정산 통화·계좌·주기, (5) 일반 모바일 브라우저 및 위챗 안에서 휴대폰 한 대로 완료 가능한 결제 방식이다. 이니시스는 오픈마켓 하위 판매자 지급대행도 안내하지만 위챗 해외 결제와 결합되는지는 별도 확인해야 한다. [지급대행 서비스 안내](https://inicis-service.inicis.com/).

중개 모델을 유지하더라도 실제 돈의 이동은 플랫폼 계좌를 거치는 방식 또는 PG가 셀러에게 정산하는 방식 중 계약·제도에 맞게 결정한다. 현재 사용자가 원하는 플랫폼 수취 경로의 실현 가능성을 먼저 확인하며, 셀러 직접 수금을 영구 운영안으로 확정하지 않는다. 결제 서비스가 존재한다는 사실은 중국에서 오렌담마켓 주문 페이지의 VPN 없는 접속 품질까지 보장하지 않는다. 아직 사업자 문의·신청·연동·실거래는 수행하지 않았다.

### 토스페이먼츠 유지·병행·교체 판단 (검토안)

현재 저장소는 토스 결제창뿐 아니라 서버 승인·취소·환불도 토스에 연결되어 있다. `lib/core/env.dart`의 카드 결제 노출 기본값은 꺼져 있으며 정식 계약 전까지 무통장입금 운영이라는 주석이 있다. 다만 실제 토스 계약 여부와 배포 환경의 활성화 여부는 이 코드만으로 확정할 수 없다.

- **병행 후보:** 국내 결제는 토스를 유지하고 중국 위챗 결제에 이니시스를 추가한다. 양사 계약 조건을 확인해야 하며, 승인·환불·정산 내역을 원래 결제대행사와 연결해서 관리하는 개발과 두 계약의 운영 부담이 생긴다.
- **통합 후보:** 이니시스가 필요한 국내 결제·중국 온라인 위챗 결제·중개 정산 구조를 승인하고 비용 조건도 적합하면 이니시스로 통합하는 안을 검토한다. 특히 토스로 실제 결제를 시작하기 전이라면 비교할 만하다. 기존 토스 거래가 있다면 해당 거래의 환불·조회·정산 처리는 전환 뒤에도 유지해야 한다.
- **선행 확인:** 토스에 위챗 지원과 중개 구조의 이용 가능 여부를 먼저 확인하고 이니시스에는 같은 거래 구조로 신규 입점·글로벌 결제·필요한 지급대행 조건을 확인한다. 토스의 계약이나 심사가 이니시스로 이전된다고 가정하지 않는다. 사전 적합성 확인 → 필요한 주문서·정책·상품 정보 준비 → 정식 심사·계약 및 연동 검증 → 실제 전환 순서로 검토한다.

이니시스 공식 신청 안내는 입점 제한 유형에 장기서비스제공(구매대행·예약상품·공동구매 등)과 소셜커머스를 포함한다. 프로젝트 이름이나 기능만으로 해당 여부를 판정하지 말고 실제 상품 확보·배송 시점과 판매 책임·자금 흐름을 공개해 확인한다. 글로벌 결제와 지급대행은 별도 신청·특약이 있고, 지급대행은 하위 판매자 등록 및 조건에 따른 고객확인 심사도 안내한다. 위챗을 제공한다는 사실만으로 오렌담마켓의 승인이나 정산 방식이 보장되지 않는다. [서비스 신청·업종 제한](https://www.inicis.com/service-application), [계약 서류·특약 안내](https://www.inicis.com/pg-docs), [지급대행 안내](https://manual.inicis.com/iniweb/opmall_aml.html).

현재는 어느 결제대행사로 교체하거나 병행하기로 결정하지 않았고, 신청·외부 문의·기능 구현을 수행하지 않았다.

## 이전 실시간 입력 제안 (2026-09-13 보류)

아래의 방송 중 전자 주문장에 고객별 주문을 입력하는 흐름은 이전 제안의 기록이다. 최신 피드백에 따라 이 방식을 첫 시험의 기본 경로로 사용하지 않는다. 방송 후 비회원 확인·청구·정산 목표는 유지하며, 현재 추천 흐름은 문서 상단의 수정안을 따른다.

현재 검토할 흐름은 **더우인 시청·채팅 주문 → 판매자 전자 주문장에 기록 → 상품·가격·구매 가능 수량 확인 → 고객별 정산서 생성 → 판매자 검토·전달 → 방송 후 고객의 주문 확인·배송지 입력 → 입금 확인 → 중국 주소로 배송**이다. 이 안에서는 판매자의 주문 입력이 남고 취합·금액 계산·정산서 작성을 자동화한다. 고객의 주문 입력까지 자동 연결하는 최종 목표는 유지하되, 더우인 연동이 가능하다고 미리 확정하지 않는다. 이 변경안 역시 아직 사용자와 검토하는 단계다.

방송 전에 준비할 것은 주문을 모을 회차와 링크 정도다. 정식 상품 등록 없이 구매 요청을 접수할 수 있어야 한다. 상품 정보는 방송 중 입력 가능한 시점이나 방송 후 정산 과정에서 보완한다.

현재 고객의 주문 메시지에는 상품을 단독으로 식별할 정보가 없으므로, 판매자나 주문 담당자가 **상품이 바뀔 때 ‘지금 판매할 상품 추가’로 새 주문칸을 만드는 방식**을 제안했다. 앞선 대화의 ‘다음 상품’은 이 동작을 가리키는 부정확한 임시 이름이었다. 예를 들어 니트를 소개할 때 니트 주문칸을 만들고, 가방을 소개할 때 가방 주문칸을 추가한다. 회차 안에서 상품을 구분하고 그 상품에 고객 ID·수량·옵션 메모를 연결한다. 사전 등록은 없어도 현장에서 짧은 이름이나 사진 등 최소한의 구분 정보를 남기는 작업은 필요하다. 사용자가 별도 담당자와 휴대폰·PC 사용 가능 여부를 확인했으므로, 이 작업은 보조 담당자가 맡는 안으로 구체화한다.

외부 방송은 시청자마다 지연이 다르므로 **주문 시각만으로 현재 상품을 자동 연결해서는 안 된다.** 고객이 보고 선택한 상품을 요청에 고정하고, 판매자가 다음 상품으로 넘어가더라도 작성 중인 요청을 새 상품으로 바꾸지 않는다. 최근 상품을 확인·선택할 수 있게 하고 상품명·사진 등 구분 정보를 보완한다. 방송 영상이나 채팅만 보고 상품 전환을 자동으로 이해하는 기능은 초기 범위가 아니다.

같은 상품을 원하는 여러 고객의 요청을 묶은 뒤, 판매자가 상품명·가격을 한 번 입력하면 해당 요청의 금액을 함께 계산하는 방식이 목표다. 요청 접수와 실제 구매 가능 확정은 구분하고, 고객 입력 가격이나 단순한 접수 시각만으로 상품·청구 금액을 확정하지 않는다.

고객이 방송 중 상품을 추가할 때마다 즉시 결제하도록 요구하는 흐름보다, 한 판매 회차의 주문을 고객별로 모아 방송 후 한 번에 정산하는 방식이 현재 업무에 맞는다. 방송 회차는 주문을 묶는 단위이며, 오렌담마켓이 영상을 직접 송출할 필요는 없다.

고객이 직접 남긴 주문을 시스템으로 받는 것이 최종 목표지만, 방송 중 외부 주문 링크를 사용하는 방식은 모바일 제약으로 보류한다. 현재 수기 기록을 대체하는 시험에서는 판매자나 주문 담당자가 채팅 주문을 **손님 ID와 함께 전자 주문장에 입력하는 방식**을 검토한다. 이후 허용된 채팅 연동이나 방송 중 사용할 수 있는 주문 기능을 확보하면 같은 주문장으로 연결한다. 고객별 취합·합계·정산서 작성에 재입력이 필요하지 않게 하고, 판매자 입력만 가능한 시스템으로 목표를 축소하지 않는다. 두 경로를 함께 사용할 때 같은 요청이 중복 기록되지 않도록 주문 출처와 확인 상태도 보존한다. 외부 방송 채팅의 자동 수집·해석은 초기 범위로 확정하지 않는다.

방송 종료 후 추가 주문을 받을지는 현장의 구매 가능 여부에 따라 판매자가 결정한다. 기존 상품 판매 기간 규칙을 현장 구매 요청에 그대로 적용한다고 가정하지 않는다.

### 보조 담당자가 있는 운영안

| 역할 | 방송 중 사용하는 화면과 업무 |
| --- | --- |
| 아내·방송 진행자 | 더우인에서 현장 상품 소개 |
| 고객 | 더우인에서 시청하며 기존처럼 채팅 주문 |
| 보조 담당자 | 채팅을 확인하면서 오렌담마켓 주문장에 상품·손님 ID·옵션·수량 기록. PC 중심 화면을 우선 검토하고 휴대폰 입력도 고려 |

구체적인 제안 순서:

1. 방송 회차를 열고, 소개가 시작되는 상품의 짧은 이름을 한 번 입력한다. 가격은 확인한 시점에 한 번 입력하고 사진은 보조 자료로 남길 수 있게 한다.
2. 그 상품의 주문이 들어올 때마다 손님 ID를 검색·선택하고 옵션과 수량을 기록한다. 상품 이름과 가격을 고객마다 반복 입력하지 않는다.
3. 다른 상품 소개가 시작되면 담당자가 새 상품을 추가한다. 늦게 도착한 이전 상품 주문도 선택해서 기록할 수 있게 한다.
4. 입력 즉시 고객별 누적 내역과 상품·옵션별 총수량을 계산한다. 수량 변경·취소 요청은 기존 기록을 수정하며 무조건 새 주문으로 누적하지 않는다.
5. 방송 후 확보 수량·가격·배송비를 검토해 고객별 정산서를 만든다. 이후 고객이 자신의 내역·중국 배송지를 확인하고 기존 방식으로 결제한다. 정산서 전달과 입금 확인은 우선 수동이다.

첫 시험의 자동화 대상은 고객별 취합·금액 계산·정산서 작성이다. 채팅을 읽고 주문을 입력하는 일은 담당자에게 남는다. 고객 입력 자동 연결은 더우인 연동 경로가 검증된 뒤 확대할 목표이며, 보조 담당자가 있다는 사실을 채팅 자동 수집 가능성으로 해석하지 않는다.

### 고객의 비회원 주문 확인·송금 안내·선택 가입 (추천안)

방송 후 지금 정산서를 전달하는 연락 채널로 고객별 전용 링크를 보내는 안을 제안한다. 고객은 오렌담마켓 계정을 만들지 않고 이번 주문의 내역·확정 금액·배송 정보를 확인하고 송금 안내까지 볼 수 있다. 링크 전달은 담당자가 하며 메시지 자동 발송은 별도다. 더우인 방송 중 외부 링크 이동을 요구하는 흐름과 구분한다.

1. **주문 확인:** 해당 고객의 상품명·옵션·수량·단가·배송비·총액과 확보 여부를 표시한다. 사진이 기록돼 있으면 함께 보여준다. 고객이 불일치한 내용을 발견하면 수정 요청을 남기고 담당자가 확인한다. 미확정 금액으로 송금을 요청하지 않는다.
2. **배송지 확인:** 필요한 중국 주소·연락처를 입력하거나 확인한다. 주소·배송비에 영향을 주는 변경은 담당자가 확인한 뒤 청구 금액을 확정한다. 회원가입을 배송에 필요한 연락처 확인과 동일시하지 않는다.
3. **송금 안내:** 확정된 금액과 해당 주문의 실제 수취인·수금 수단을 한곳에 안내한다. 플랫폼 수금 주문은 플랫폼의 수금 안내를 사용하고, 현재 아내 명의의 중국 계좌·개인 위챗 송금은 셀러 직접 수금으로 명시한다. 모바일 한 대에서 결제 안내를 따라갈 수 있어야 하므로 같은 휴대폰 화면에 띄운 QR을 다른 카메라로 스캔하는 흐름만 제공하지 않는다.
4. **송금 알림과 확인:** 고객의 ‘송금했어요’는 입금 확인 대기 요청이다. 실제 수금 내역을 확인할 권한이 있는 운영자가 대조한 뒤에만 입금 확인으로 바꾼다. 플랫폼 수금과 셀러 수금을 구분하며 고객의 체크·캡처·페이지 복귀만으로 결제 완료를 확정하지 않는다.
5. **선택 가입:** 주문 확인이나 송금 알림 이후 ‘주소와 주문 내역을 저장해 다음에도 편하게 이용하기’를 제안한다. 계정 생성과 저장 목적을 분명히 알리고 고객이 선택하게 한다. 가입하지 않아도 이번 주문의 결제 안내·입금 상태·배송 상태를 확인할 수 있게 한다.

고객 편의의 제안 범위:

| 이용 방식 | 고객이 얻는 편의 |
| --- | --- |
| 비회원 전용 링크 | 이번 주문과 금액 확인, 수정 요청, 배송 정보 확인, 송금 안내, 입금·배송 상태 조회 |
| 선택 가입 | 여러 방송에서 산 내역을 한곳에서 확인, 다음 주문 때 주소·연락처 재사용, 정산서 링크를 다시 찾는 수고 감소 |

회원가입 혜택은 반복 구매의 편의부터 검증한다. 적립·할인·합배송 절감은 비용과 실제 운영 규칙을 확인하기 전 기본 혜택으로 약속하지 않는다. 가입을 하지 않아도 필요한 주문 확인과 사후 처리가 가능해야 한다.

고객 기록과 로그인 계정은 구분한다. 담당자는 비회원 고객의 방송 ID와 주문을 기록할 수 있고, 나중에 가입하면 본인 확인을 거쳐 해당 주문을 계정에 연결한다. 닉네임 일치만으로 과거 주문을 연결하지 않는다. 전용 링크는 추측하기 어려운 개별 접근 수단으로 만들고 범위·유효기간·재발급을 관리한다. 전체 주소 등 민감 정보 조회·변경과 과거 주문 전체 연결에는 별도 본인 확인을 검토한다. 구체적인 인증 수단은 중국 고객의 접근성을 확인한 뒤 결정한다.

공식 위챗페이는 일반 모바일 브라우저용 H5 결제 등 상점 결제 제품을 제공하지만 사업자·앱 등 이용 조건과 권한이 있다. 개인 계정 송금이 된다는 사실만으로 오렌담마켓의 결제 버튼에서 금액을 전달하고 결과를 자동 확인할 수 있다고 가정하지 않는다. 향후 상점용 결제 연동을 검토할 때 실제 수취 주체·한국 사업자의 이용 경로·접속 환경별 권한을 확인한다. [공식 H5 결제 소개](https://pay.wechatpay.cn/doc/v3/merchant/4012791832), [위챗페이 상점 플랫폼](https://pay.wechatpay.cn/).

초기 검증은 가입자 수만으로 평가하지 않는다. 고객의 정산서 열람·주문 확인·송금 완료·반복 문의 감소를 먼저 보고, 재구매 고객이 주소와 주문 이력 저장을 실제로 사용하는지 확인한다. 중국 고객의 VPN 없는 모바일 접속도 필수 검증 대상으로 유지한다.

## 더우인 위에 독립된 주문창을 띄우는 경로 (2026-09-13)

사용자는 더우인 내부의 미니프로그램 대신 자신이 만든 웹·앱을 더우인 화면 위에 겹쳐 띄우는 방법을 질문했다. 고객 휴대폰 구성에 대한 답은 ‘둘 다 많거나 아직 모름’이므로 안드로이드가 다수라고 가정하지 않는다. 기능 구현은 여전히 요청하지 않았다.

- **안드로이드 설치 앱:** 운영체제의 다른 앱 위 표시 기능으로 작은 오렌담마켓 버튼과 주문 패널을 만드는 것이 기술적으로 가능하다. 고객의 앱 설치와 명시적인 표시 권한 허용이 필요하다. 일반 앱 화면보다 위에 표시하는 `TYPE_APPLICATION_OVERLAY` 및 `SYSTEM_ALERT_WINDOW` 경로이며, 웹 주소 접속만으로 얻는 권한은 아니다. 더우인의 미니프로그램 화면을 수정하거나 방송 영상을 재송출하는 방식도 아니다. [안드로이드 창 기능](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY), [사용자 표시 권한](https://developer.android.com/reference/android/provider/Settings#canDrawOverlays(android.content.Context)).
- **더우인·단말 동작 미검증:** 안드로이드는 앱이 다른 앱의 겹친 창을 숨기도록 선택할 수 있게 한다. 현재 더우인이 실제 시청 화면에서 이를 사용하는지는 확인하지 않았다. 주문 패널 표시·터치 중 방송 영상과 소리가 계속 재생되는지, 창이 사라지지 않는지, 손님 기종의 권한·백그라운드 설정과 중국 네트워크에서도 주문이 저장되는지 실기기 검증이 필요하다. 차단된 창을 강제로 우회하는 계획은 아니다. [앱의 겹친 창 차단 기능](https://developer.android.com/security/fraud-prevention/activities).
- **아이폰:** 일반 설치 앱이 다른 앱 위에 자유로운 웹·주문 입력창을 띄우는 안드로이드 방식은 공통 구현 경로로 삼을 수 없다. 애플의 PiP는 영상 재생·영상 통화를 위한 기능이며 임의의 터치 주문 폼을 띄우는 것과 다르다. 애플 DTS의 iPadOS 작업공간 위 주석 오버레이 답변도 해당 공개 기능이 없다고 설명하지만, 이를 모든 애플 기기의 멀티태스킹 자체가 불가능하다는 뜻으로 확대하지 않는다. [애플 PiP](https://developer.apple.com/documentation/avkit/adopting-picture-in-picture-in-a-standard-player), [애플의 작업공간 오버레이 답변](https://developer.apple.com/forums/thread/832639).
- **일반 모바일 웹:** 오렌담마켓 페이지 자체가 다른 앱 위에 자유로운 입력창을 띄우는 기능을 표준 고객 경로로 제공할 수 있다고 가정하지 않는다. 브라우저의 동영상 PiP와 주문 폼은 구분한다. Chrome의 임의 HTML 창을 위한 Document PiP 공식 출시 안내는 데스크톱을 대상으로 한다. 기기 자체의 분할 화면·작은 창 기능이 있다면 별도 이용 후보일 수 있지만 아이폰·안드로이드 공통 동작으로 약속하지 않는다. [Chrome Document PiP](https://developer.chrome.com/docs/web-platform/document-picture-in-picture).

안드로이드 후보 동선은 **고객이 앱 설치·표시 허용·방송 회차 선택 → 더우인 시청 → 오렌담마켓 버튼으로 상품 확인·색상·수량 선택 → 구매 요청 저장 후 창 접기 → 방송 후 주문 확인·결제**다. 동시 시청 여부가 시험에서 확인되면 고객이 직접 주문하므로 담당자의 고객별 실시간 타이핑을 줄일 수 있다. 다만 상품 정보는 현장에서 한 번 식별해 공유해야 하며, 요청 작성 중 상품을 자동 교체하거나 영상 지연을 무시하고 서버의 현재 상품만 선택하게 해서는 안 된다.

겹친 창 권한이 더우인 고객 ID·채팅 접근 권한을 제공하는 것은 아니다. 비회원 주문을 허용하더라도 고객과 방송 ID를 연결하는 절차는 별도로 필요하다. 설치·권한 허용은 회원가입과도 별개이며 고객 부담으로 비교한다. 기존 채팅 주문과 직접 주문을 병행할 때 중복 집계를 방지한다. 플랫폼 약관·배포·결제 승인과 운영체제 표시 기능은 각각 확인해야 하며, 표시가 된다는 이유로 외부 판매·수금이 승인됐다고 보지 않는다.

현재는 안드로이드 고객용 선택 기능 후보이며, 고객 기종과 실제 더우인 위 동작을 검증하기 전 전체 고객의 유일한 주문 경로로 정하지 않는다. 방송 후 취합·비회원 주문서 방식과 더우인 내 공식 연결 가능성도 계속 검토한다.

## 더우인 안에서 오렌담마켓을 여는 경로 (2026-09-13 재확인)

사용자가 고객의 앱 전환 없이 더우인 안에서 오렌담마켓을 여는 방법을 재검토해 달라고 했다. 앱 내부에서 페이지가 열리는 것, 방송을 계속 보며 주문하는 것, 외부 주문·결제를 허용받는 것은 서로 다른 조건이다.

- **일반 웹페이지 표시:** 더우인 미니프로그램에는 등록·검증한 도메인의 웹페이지를 표시하는 `web-view`가 있다. 공식 설명은 페이지 전체를 채우며 개인 유형 미니프로그램은 지원하지 않는다고 안내한다. 웹을 표시할 수 있다는 사실만으로 라이브 위에 임의의 오렌담마켓 창을 띄우거나 시청을 계속하며 주문할 수 있다고 보장하지 않는다. 현재 Flutter 웹의 실제 호환성·중국 접속 품질도 미검증이다. [웹페이지 표시 기능](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/develop/component/open-capacity/web-view).
- **라이브의 미니프로그램 입구:** 일반 라이브 연결 기능은 심사를 통과한 미니프로그램을 방송 계정에 연결하고 라이브의 입구에서 해당 페이지를 여는 방식이다. 공개 안내의 기업 주체·출시·허용 업종·계정 연결·능력 신청 조건을 확인해야 한다. 이를 모든 판매용 미니프로그램에 사용할 수 있다고 해석하지 않는다. [라이브 연결 안내](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/flow-entrance/douyin/live/self-mount).
- **상품 주문 용도의 제한:** 전자상거래 플러그인 입점은 기업 대상의 특정 분야 초청 방식이다. 해당 능력 목록은 라이브 연결을 일반적으로 열지 않고 추천 구매 안내 분야의 일부 초청 사례만 명시하며 주문·결제는 抖店의 거래·결제 기능을 사용하도록 한다. 따라서 오렌담마켓 주문과 KG이니시스·개인 위챗 수금을 그대로 미니프로그램 안으로 옮기는 계획을 확정하지 않는다. [판매용 입점 조건](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/Industry/online-retailers/access-guide), [판매용 기능 범위](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/Industry/online-retailers/capacity-inventory).
- **외부 유도·동시 시청:** 라이브 연결 FAQ는 제3자 연락처 추가나 다른 플랫폼으로의 유도를 제한한다. 결제대행사 승인과 더우인의 판매·연결 승인은 별개다. 공식 상호작용 도구에서 말하는 반화면 패널은 방송 진행자의 도구 설정 화면이므로 고객용 주문 패널의 근거로 사용하지 않는다. 라이브 미리보기 기능은 별도로 존재하지만 오렌담마켓의 판매 용도에서 장시간 동시 시청·주문이 가능한지는 확인하지 못했다. [라이브 FAQ](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/flow-entrance/douyin/live/faq), [상호작용 도구 패널](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/development/tutorial/app-interaction-guide), [라이브 연결·미리보기](https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/operation/live-status-component).

따라서 더우인 안의 주문 입구는 검토 후보로 남기되, 현재 계정·한국 사업자·실제 판매 품목으로 승인 가능한 경로가 있는지 먼저 확인한다. 일반 개발자 입점 API에 해외 주체가 정의되어 있다는 사실은 판매용 미니프로그램 자격을 보장하지 않으며 중국 법인이 없다는 사실만으로 모든 경로를 불가능하다고 단정하지도 않는다. 허용된 주문 경로를 확보한다면 그 주문을 오렌담마켓의 관리·정산에 연결할 수 있는지 검토한다. 방송 후 취합안 역시 후보로 유지하며 이번 질문으로 특정 방식의 채택·구현이 승인된 것은 아니다.

## 더우인 연동 검토 (2026-09-12 공식 공개 문서 확인)

- **더우인 안의 자체 주문창:** 전자상거래 플러그인 미니프로그램은 제한된 분야의 초청 입점 방식이다. 해당 능력 목록은 방송 연결을 일반적으로 개방하지 않고 일부 초청 사례만 허용하며, 주문·결제는 抖店의 기능을 사용한다고 명시한다. 임의의 오렌담마켓 주문창을 방송에 붙여 기존 중국 계좌·위챗페이 정산을 그대로 연결할 수 있다고 가정하지 않는다. [입점 안내](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/Industry/online-retailers/access-guide), [능력 목록](https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/Industry/online-retailers/capacity-inventory).
- **채팅 자동 수신:** 라이브 상호작용 도구에 댓글·사용자 ID 수신 능력은 있으나, 현재 접속 안내 상단에 신규 플러그인 접수를 중단한다고 적혀 있다. 기술 문서의 존재만으로 신규 주문 도구의 신청·외부 전송·판매 용도 승인을 보장하지 않는다. 다른 승인된 공급업체나 계정별 권한으로 이용 가능한 경로가 있는지는 미확인이다. [상호작용 도구 접속 안내](https://developer.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/introduction/interactive-tools-guide).
- **오렌담마켓 안에서 더우인 방송 재생:** 공식 SDK 경로가 있으나 일반 웹페이지에 방송 링크를 넣는 방식과 다르다. 공개 접속 안내에는 앱 마켓 출시·신청·심사와 일간 활성 사용자 10만 명 조건 등이 기재돼 있다. 별도 홍보 문서와 기술 문서의 범위·지원 OS 설명에도 차이가 있어 실제 신청 가능 여부와 지원 범위는 공식 확인이 필요하다. 초기 소규모 시험에서 바로 쓸 수 있는 수단으로 확정하지 않는다. [SDK 접속 절차](https://developer.open-douyin.com/docs/resource/zh-CN/dop/ability/douyin-live-sdk/introduction), [SDK 솔루션](https://developer.open-douyin.com/docs/resource/zh-CN/dop/ability/douyin-live-sdk/solution), [참여 프로그램](https://developer.open-douyin.com/docs/resource/zh-CN/dop/ability/douyin-live-sdk/douyin-sdk-sound-plan).

이에 따라 현재 제안은 고객의 더우인 채팅 이용을 유지하면서 판매자 업무를 먼저 전산화하고, 채팅 수집이나 방송 내 주문 기능은 실제 사용 자격과 동작을 확인한 뒤 계획에 포함하는 것이다. ‘빨간색 하나’만으로 상품까지 자동 확정할 수는 없으므로, 수집 경로를 확보해도 상품 연결·수정·취소 확인은 별도 문제로 남는다. 고객 웹 직접 주문은 방송 후 또는 시청과 주문을 함께 할 수 있는 환경에서 사용할 후속 후보로 유지한다.

## 이 프로젝트에 추가할지에 대한 추천안 (미확정)

현재 코드 검토에 따른 추천은 **같은 프로젝트 안에 독립된 ‘방송 주문 관리’ 기능을 두고 아내와 보조 담당자의 업무로 시험하는 것**이다. 이는 사용자가 채택하거나 구현을 지시한 결정이 아니다.

기존 서비스는 등록 상품을 고객이 고르고 금액·재고를 확인해 주문하는 입점형 쇼핑몰이다. 이번 기능은 현장에서 받은 요청을 모아 가격·확보 수량을 확인한 뒤 고객에게 청구하는 판매자 업무 도구다. 같은 판매자·서비스를 다루므로 공통 기반을 활용할 이유는 있지만, 주문 규칙의 차이가 크므로 화면 몇 개를 덧붙이는 수준으로 추정하지 않는다.

첫 범위는 판매자 영역의 방송 주문장과 고객별 정산서로 제한해 입력 속도·누락·중복·방송 후 정리 시간을 검증한다. 공통 코드와 서버를 이용하더라도 같은 주문 표·고객 로그인·취소 기한을 강제로 공유할 필요는 없다. 고객용 웹의 중국 접속 성능은 별도 검증 대상이며, 필요하면 고객용 화면의 제공 방식도 조정한다.

향후 방송 주문 관리가 별도 브랜드·고객군·운영팀·배포 주기를 갖는 독립 사업이 되면 프로젝트 분리를 다시 판단한다. 지금부터 별도 앱·서버를 유지하는 비용을 늘리기보다, 업무 경계를 분명히 두어 실제 시험 결과에 따라 선택할 수 있게 하는 안이다.

## 우선 맞춰야 할 부분

### 고객의 주문 진입 방식

현재 장바구니와 주문은 로그인이 필요하고, 로그인 화면에는 카카오만 노출된다. 추천안은 방송 주문에 대해 비회원 전용 링크로 주문 확인과 송금 안내를 제공하고, 계정 가입은 주소·주문 이력 저장을 원하는 고객이 선택하게 하는 것이다. 구체적인 본인 확인·로그인 수단은 아직 결정하지 않았다. 현재 기록하는 방송 손님 ID가 고유 계정 ID인지 표시 닉네임인지는 미확인이다. 입력한 원래 ID를 보존하면서 방송 플랫폼과 고객 기록을 연결하고, 고객의 웹 계정과도 확인 후 연결해야 한다. 같은 닉네임이나 단순 문자열 일치만으로 다른 고객의 주문을 합치거나 공개하지 않는다.

관련 파일: [app_router.dart](../lib/router/app_router.dart), [login_page.dart](../lib/features/auth/login_page.dart).

로그인 방식을 변경할 때는 `orders.user_id`, 주문 RPC의 `auth.uid()`, 주문 조회 권한도 함께 검토해야 한다. 현재 DB는 로그인한 구매자를 전제로 한다.

### 배송지 입력

현재 기본 주소는 직접 입력할 수 없고 한국 우편번호 검색을 통해 채운다. 실제 배송지는 중국 내 고객 본인 주소이므로, 중국 주소와 연락처를 입력·저장할 수 있게 변경해야 한다. 상품을 추가할 때마다 배송지를 반복 입력하는 방식은 피하고 고객별 정산·배송 정보와 연결한다.

관련 파일: [checkout_page.dart](../lib/features/orders/checkout_page.dart).

### 결제 확인과 입금 기한

현재 주문은 원화 금액과 플랫폼의 한국 계좌 무통장입금 중심이고, 카드결제는 기본 비활성이다. 사용자는 플랫폼이 수금한 뒤 셀러에게 정산하는 모델과 방송 주문을 결합하려 한다. 한편 현재 중국 방송은 아내 명의의 계좌·개인 위챗으로 수금하므로 셀러 직접 수금이다. 고객 청구서의 실제 수취인, 입금 확인 권한, 플랫폼의 셀러 지급액 또는 수수료 수취액을 수금 방식별로 구분한다. 플랫폼 수금으로 일원화할 중국 결제 경로는 아직 확보됐다고 가정하지 않는다.

첫 버전에서는 고객별 상품·수량·금액과 정산서를 자동 생성하고, 판매자가 확인한 후 정산서 링크를 복사해 전달하는 방식을 추천한다. 링크에는 본인 주문을 안전하게 조회할 수 있는 접근 방식이 필요하다. 정산서 전달 채널의 자동 발송 연동은 아직 확정하지 않았다.

입금 확인은 초기에는 사람이 처리할 수 있다. 고객이 입금했다고 표시하거나 증빙을 올리는 것을 실제 결제 완료로 자동 처리하지 않는다. 은행·결제 서비스 연동이 확인되기 전에는 입금 자동 확인을 구현 범위로 확정하지 않는다.

기존 미입금 자동 취소는 일반 무통장 주문 24시간, MOQ 상품은 마감 판정과 연결된다. 방송 중 주문을 누적하고 방송 후 정산서를 발행하는 흐름에는 기한의 시작점·재고 확보 시점·취소 규칙을 다시 맞춰야 한다.

### 판매자의 반복 작업

고객별 구매 요청 취합·상품 연결·합계·정산서 생성이 우선이다. 방송 중 판매자에게 기존 상품 등록 폼이나 고객별 주문을 모두 입력하도록 요구하지 않는다. 채팅 또는 현재 수기 기록을 원본으로 방송 후 주문 초안을 작성하고 사람이 확인하는 안을 검토한다. 상품 단가를 한 번 입력하면 같은 상품에 연결된 요청의 잠정 금액을 함께 계산한다. 가격 미확인 요청은 0원 확정으로 취급하지 않으며, 확정·발행한 정산서는 이후 상품 가격 변경으로 조용히 바뀌지 않게 한다. 상품별 수량 집계와 미입금·미발송 목록을 연결하면 주문을 옮겨 적는 일을 줄일 수 있다. 합배송과 배송비 계산 방식은 후속 확인 대상으로 둔다.

| 방송 후 초안 | 보존된 채팅 또는 수기 기록의 인식·전산화 후보를 시험. 원본과 연결해 고객·상품·수량·변경·취소를 담당자가 확인 |

## 구현 전에 남은 업무 결정

- 현재 수기로 기록하는 손님 ID의 성격(더우인 고유 계정 ID 또는 표시 닉네임)
- 현재 수기 기록이 주문 집중 구간의 속도를 따라가는지와 실제 기록 형식
- 고객 식별 정보·주문 전문이 빠짐없이 남는 채팅 보존 경로, 상품 전환 식별 방법 및 인식 후 검수 부담
- 더우인 계정의 상점·공식 연동 권한 및 사용 가능한 채팅 기록 경로
- 보조 담당자의 주 사용 기기와 빠른 주문 기록 방식, 방송 중·후에 보완할 항목
- 고객 식별·로그인·정산서 조회 방법
- 실제 상품 가격과 청구 통화, 환율 적용 여부
- 중국 주문을 플랫폼 수금으로 일원화할 실제 결제 경로 또는 셀러 직접 수금 병행 여부
- 수금·입금 확인·셀러 지급 권한, 수수료 약정·정산 시점·환불 반영 기준과 통화
- 배송비·추가금 산정, 합배송·주문 수정·취소 방식
- 방송 회차 마감, 정산서 확정·발행 시점, 입금 기한
- 정산서의 필수 항목과 전달 채널

이후에는 실제 정산서 한 건의 항목과 고객 주문이 확정되는 시점을 기준으로 화면과 데이터 구조를 구체화한다.

## 실행 순서와 검증 기준

1. 상품 한 개에 최대 20건이 들어오는 실제 구간에서 채팅 기록 확보 가능 여부와 현재 수기 형식을 확인한다. 고객 식별·주문 누락·상품 구분과 방송 중 추가 대기 여부를 평가한다. 방송 후 취합할 수 있다는 확인을 전제로 한다.
2. 확보한 원본으로 방송 후 주문 초안을 만드는 후보를 평가한다. 현재 수기 자료도 인식 후보이자 대조 자료로 삼고, 정확도뿐 아니라 수정·검수 시간을 비교한다. 자료 확보와 오류 처리 검증 전에 채팅 자동 수집·AI 완전 자동 주문을 약속하지 않는다.
3. 방송 마감 후 고객별 청구서를 생성·검토·전달하고, 실제 수금 주체별 입금 확인·배송·셀러 정산으로 이어가도록 한다. 일반 주문과 방송 주문의 정산 집계가 중복되지 않는지도 검증한다.
4. 연길 고객이 VPN 없이 일반 브라우저에서 방송 후 주문 내역·정산서를 확인할 수 있는지 실기기 검증한다. 방송 중 직접 주문 경로를 채택한다면 휴대폰 한 대에서 시청이 끊기지 않는지도 함께 검증한다.
5. 고객 입력을 다시 메신저나 엑셀에서 옮겨 적어야 하는 단계가 얼마나 줄었는지 확인한다.
6. 주문 흐름이 자리 잡은 뒤 결제·배송 연동 자동화와 국내 자체 라이브를 검토한다. 중국 자체 라이브는 별도 후속 과제로 둔다.

기존 쇼핑몰의 주문·셀러 정산 경로를 연결해 실거래를 검증할 때는 [초기 검토의 MOQ 부분 취소·정산 문제](reviews/2026-09-12-project-review.md)도 해결해야 한다. 독립된 방송 주문장은 그 업무에 맞는 상품 연결·청구 금액·담당자 권한을 별도로 검증한다.

대화에서 판매자 입력·고객 직접 입력·상품 전환·고객별 누적·단가 일괄 반영을 살펴보는 작동 예시를 만들었다. 예시 금액 단위인 위안은 화면 설명용이며 실제 청구 통화 결정이 아니다. 예시는 서버 저장·고객 본인 확인·정산서 발행을 구현한 제품 기능이 아니다.

이번 작업은 우선순위와 기존 구현의 차이를 기록하고 화면 흐름을 검토한 것이다. 앱의 주문 기능 수정·계정 가입·운영 배포는 수행하지 않았다.
