# 더우인 녹화본에서 주문 채팅 추출: 정확도·개발·비용·시간 검토

조사일: 2026-09-13. **계획 단계이며 기능 구현·모델 설치·유료 API 실행은 하지 않았다. 실제 녹화본과 처리 장비를 시험하지 않았다.**

## 확인된 조건과 판단

- 방송은 한 회 **3~4시간**, 주문 채팅은 **한국어가 대부분**이다. PC와 휴대폰 화면 녹화 모두 가능하다.
- 고객은 상품 번호 없이 “2개”, “빨간색으로 한 개”처럼 현재 상품을 주문한다. 상품 사전 등록은 불가능하다.
- 상품 하나에 최대 20건의 주문이 들어온다. 보조 담당자가 모든 주문을 입력할 때까지 방송을 기다릴 수 없으며 **방송 후 취합은 가능**하다.
- 현재 손님 ID와 함께 수기로 기록하고, 방송 후 고객별 정산서를 보낸다.

추천 검증 대상은 **PC에서 채팅을 읽기 좋게 화면 녹화 → 채팅과 주문 초안 추출 → 원본을 보며 검수 → 고객별 주문장·정산서 생성**이다. 고객의 방송 중 앱 전환이나 회원가입을 요구하지 않는다. 지금은 방법의 실용성을 검증하는 단계이며 채택한 구현안은 아니다.

핵심은 글자 인식 자체보다 화면에 주문이 빠짐없이 남는지, 고객과 상품을 구분할 수 있는지, 검수가 수기 정리보다 빨라지는지다. 화면에 나오지 않은 댓글·잘린 이름은 OCR로 복구할 수 없다. 시청 화면에 보이는 이름이 고유 계정 ID인지 별명인지도 별도 확인해야 한다.

## 1. 녹화와 처리 방식

1. **채팅이 포함된 원본 화면을 보존한다.** 방송 영상만 있는 다시보기와 구분한다. 가능하면 PC에서 채팅 영역을 크게 확보하고 이름이 잘리지 않게 한다. 원본에서 글자를 키우는 것이 우선이다. 영상과 분리된 고정 배경 채팅 영역을 확보할 수 있는지는 실제 더우인 환경에서 확인한다.
2. **영상의 채팅 영역만 추출한다.** 원본 녹화는 예를 들어 30fps로 보존하고, OCR 분석은 우선 2fps와 변화 구간 추가 추출을 비교한다. 2fps가 모든 주문을 잡는다는 뜻은 아니다. 댓글이 짧게 나타나거나 한꺼번에 밀리는 구간에서 누락을 측정해야 한다. 움직이는 영상이 채팅 배경에 깔리면 단순 화면 변화 비교만으로는 처리량이 줄지 않을 수 있다.
3. **한글 본문과 표시 이름을 읽는다.** 한국어 모델과 다국어 클라우드 OCR을 같은 표본으로 비교한다. 이름에 중국어·영문·이모지가 있는 경우를 포함한다.
4. **여러 화면에 반복 등장하는 동일 댓글을 추적한다.** 위치 이동과 전후 시각을 함께 사용한다. 같은 사람이 나중에 다시 쓴 “2개”를 전역 문자열 중복 제거로 삭제하면 안 된다. 긴 영상을 나눠 처리할 때 경계에 걸친 댓글도 이어서 추적한다.
5. **채팅을 주문 후보로 분류한다.** 주문·질문·추가 주문·수량 변경·취소를 구분한다. “두 개로 바꿀게요”를 기존 주문에 두 개 더하는 것으로 처리하지 않는다. 애매한 문장은 원문 그대로 확인 대상으로 남긴다.
6. **상품을 연결한다.** 가능하면 보조 담당자는 상품이 바뀌는 시각만 한 번 표시한다. 상품명·가격은 방송 후 보완할 수 있다. 방송 중 표시가 어려우면 녹화 영상을 보며 상품 구간을 나누는 시간이 추가된다. 방송 지연·늦은 댓글 때문에 전환 시각만으로 상품을 확정하지 않는다.
7. **검수 후 내보낸다.** 원본 시각·채팅 이미지·고객 이름·상품·옵션·수량을 함께 확인하고, 가격과 확보 수량을 확정한다. 시간순 채팅 원장, 주문 초안, 확인 필요 목록, 고객별 정산서를 구분한다. 초기에는 모든 주문을 확인하며 초안에서 바로 청구하지 않는다.

보조 담당자는 방송 중 고객별 20건을 입력하지 않아도 된다. 다만 녹화의 완전성과 사후 검수 부담을 확인하기 전까지 현재 수기 기록을 없애는 결정을 내리지는 않는다.

## 2. 인식률: 공개 수치와 실제 주문 정확도

PaddleX 공식 문서의 `korean_PP-OCRv5_mobile_rec`는 평균 인식 정확도 **90.45%**를 제시하고 한국어·영어·숫자를 지원한다. 이는 해당 평가 자료에서의 **문자열 인식 모델 성능**이며 더우인 전체 댓글 포착률, 고객 구분, 상품 연결, 주문 완성 정확도가 아니다. 한국어 전용 모델 하나가 중국어 닉네임까지 처리한다고 가정하지 않는다. [공식 한국어 모델 표](https://paddlepaddle.github.io/PaddleX/latest/en/pipeline_usage/tutorials/ocr_pipelines/OCR.html).

Google Cloud Vision은 한국어를 지원하며 한 이미지 안의 여러 언어도 인식할 수 있다. 따라서 한국어 주문과 다른 언어의 닉네임이 섞인 표본의 비교 후보가 된다. 이 지원 설명에는 우리 녹화본의 정확도 보장이 없다. [공식 언어 지원](https://docs.cloud.google.com/vision/docs/languages).

현재 자료만으로 “95~99% 정확하게 주문이 만들어진다”는 수치를 제시할 근거는 없다. 아래를 따로 측정한다.

| 지표 | 확인할 내용 |
| --- | --- |
| 원본 포착 | 실제 주문 중 화면에 표시되고 녹화에 남은 비율. 화면에 없는 주문은 별도 기록과 대조해야 파악 가능 |
| 댓글 복원 | 녹화에서 사람이 읽을 수 있는 주문 댓글 중 추출된 비율, 본문과 이름의 정확성 |
| 주문 일치 | 고객·상품·옵션·수량이 모두 맞는 비율, 변경·취소 반영 여부 |
| 잘못된 추가 | 반복 화면 때문에 생긴 중복 주문, 질문을 주문으로 잘못 넣은 건수 |
| 사람의 부담 | 정정·고객 식별·상품 연결에 쓴 시간과 기존 수기 정리 대비 절감 시간 |

가령 네 항목이 각각 98% 정확하고 오류가 서로 독립이라고 **가정**해도 모두 맞는 비율은 `0.98^4 ≈ 92.24%`다. 실제 예상 인식률이 아니라 글자 인식률을 주문 정확도로 바꿔 말할 수 없는 이유를 보여주는 계산이다. 인식기가 주는 신뢰도도 주문이 맞을 확률과 동일하지 않다.

## 3. OCR 비용 시나리오

Google Cloud Vision의 Text Detection 공개 단가는 월 1,001~5,000,000단위 구간에서 **이미지 1,000장당 US$1.50**다. 첫 1,000단위 무료는 월 단위이며 방송마다 새로 생기는 무료분이 아니다. 이미지 한 장에 여러 댓글이 있어도 OCR 기능 한 번이면 한 단위다. 다른 기능 추가·재인식은 비용을 늘릴 수 있다. [공식 요금](https://cloud.google.com/vision/pricing).

다음은 **무료분을 빼지 않은 OCR 단독 비용**이다. 저장·전송·다른 AI 호출·장비·개발·검수 인건비·세금은 포함하지 않았다. 환율을 고정하지 않기 위해 USD로 표기한다.

| OCR 입력 이미지 수 | OCR 비용 | 시나리오 설명 |
| --- | ---: | --- |
| 2,000장 | $3.00 | 변화가 적거나 처리 대상을 많이 줄인 경우의 계산 예 |
| 6,000장 | $9.00 | 아래 시간 계산에 쓰는 가정. 실제 방송에서 측정한 장수 아님 |
| 10,000장 | $15.00 | 처리 대상이 더 많은 경우의 계산 예 |
| 21,600장 | $32.40 | 3시간을 2fps로 추출해 모두 OCR하는 경우 |
| 28,800장 | $43.20 | 4시간을 2fps로 추출해 모두 OCR하는 경우 |

6,000장은 주문 6,000건이라는 뜻이 아니다. 한 이미지에 여러 댓글이 포함되고 같은 댓글이 여러 이미지에 반복될 수 있다. 2fps에서 6,000장으로 줄이려면 3~4시간의 후보 화면 중 약 21~28%만 OCR해야 하므로, 그러면서도 누락이 없는지는 반드시 시험해야 한다. 고밀도 구간에서 더 자주 추출하거나 재인식하면 위 금액보다 증가할 수 있다.

월 20회, 매회 6,000장이라는 **운영량 가정**이면 OCR은 무료분 차감 전 월 $180이다. 첫 달 할인에 기대지 않고 장기 운영비를 비교하기 위한 계산이다.

로컬 공개 OCR을 사용하면 외부 OCR API 호출료를 없앨 수 있지만 연산 장비·전기·관리 시간이 든다. 로컬 처리 후 6,000장 중 10~20%만 클라우드 재인식한다고 가정하면 추가 OCR은 $0.90~$1.80다. 단, 인식기가 확신하면서 틀리는 경우도 있어 낮은 신뢰도만 재처리한다고 모든 오류를 잡는 것은 아니다.

복잡한 채팅 해석에 언어 모델을 추가한다면 별도 비용이다. 첫 검증에서는 OCR 비용과 해석 비용을 분리하고, 단순 수량·색상은 규칙으로 처리하는 안과 비교한다. 아직 모델·입출력량이 정해지지 않아 AI 해석 비용을 확정하지 않는다.

## 4. 실제 내보내기까지 얼마나 걸리는가

**아래 시간은 실측이 아닌 조건부 산정이다.** 방송 길이만으로 처리 시간을 확정할 수 없다. 총시간은 파일 전달 + 화면 추출 + OCR + 댓글·주문 정리 + 사람의 검수 + 최종 파일 생성으로 나뉜다.

### 클라우드 OCR: 6,000장 처리 가정

파일이 처리할 PC에 이미 있고, OCR 호출을 여러 개 동시에 보내 실효 처리량이 초당 5~10장 나오며, 큰 재처리나 오류가 없는 경우를 가정한다.

| 단계 | 산정 시간 | 근거·제약 |
| --- | ---: | --- |
| 영상 읽기·채팅 영역 추출·화면 선택 | 5~20분 | 장비·코덱·영상 해상도를 모르는 상태의 개발 계획상 여유 시간 |
| 6,000장 OCR | 10~20분 | `6,000 ÷ 초당 5~10장 ÷ 60` |
| 댓글 연결·주문 후보 정리·파일 생성 | 5~15분 | 구현·모델 선택 전 작업 예산. 재처리와 사람의 검수 제외 |
| **주문 초안까지** | **20~55분, 계획상 약 20~60분** | 위 조건이 충족될 때의 합계 |

Google의 기본 텍스트 인식 할당량은 분당 1,800 이미지/페이지 수준이지만 **허용 한도이지 처리 속도 보장이 아니다**. 초당 5~10장은 실제 네트워크·동시 호출·서비스 응답을 측정해 바꿔야 할 가정이다. 녹화 PC에서 채팅 이미지만 전송하는 구성이라도 해당 이미지 전송과 API 응답이 이 처리량을 충족해야 한다. [공식 할당량](https://docs.cloud.google.com/vision/quotas).

화면을 줄이지 못해 4시간의 28,800장을 처리하면 같은 가정에서 OCR만 48~96분, 전후 작업 포함 초안까지 약 **1~2.2시간**이다. 2fps보다 자주 분석하거나 대기·재시도가 많으면 더 길어진다.

### 로컬 OCR과 장비

PaddleOCR의 공개 PP-OCRv5 일반 이미지 파이프라인 자료는 모바일 모델 조합에서 이미지당 GPU **0.62초**, CPU **1.75초**를 보고한다. V100 GPU·Xeon 서버 CPU 및 일반 이미지 평가 환경이며 한국어 채팅 녹화 시험이 아니다. 이 시간을 6,000장에 단순 곱하면 OCR만 각각 62분·175분이다. [공식 파이프라인 벤치마크](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5.en.md).

채팅 영역 크기·글자 수·한국어 모델·최적화에 따라 실제로 더 빠르거나 느릴 수 있다. 별도 GPU 없는 장비에서 이미지당 1~4초가 걸린다는 **가정**이면 OCR만 100~400분이고, 전후 작업까지 대략 2~7시간의 작업 예산이 된다. 이것을 현재 PC나 Synology NAS의 성능 예측으로 쓰지는 않는다. 모델 표의 “한 줄 인식 몇 ms”를 전체 녹화 처리 시간으로 환산해서도 안 된다.

### 업로드가 더 오래 걸릴 수 있음

4시간을 평균 6Mbps로 녹화한다고 **가정**하면 파일은 약 10.8GB다. 전체 파일을 서버로 전송할 때 업로드 20Mbps면 이상적인 최소 전송 시간부터 72분, 100Mbps면 14.4분이다. 실제 전송은 더 오래 걸릴 수 있다. 녹화가 PC에 있으면 그 PC에서 채팅 이미지만 추출해 전송하는 구성을 먼저 비교한다. 휴대폰 녹화는 파일을 PC로 옮기는 시간도 잰다.

### 사람이 확인하는 시간과 최종 파일 생성

검수는 방송 길이보다 주문 수·오류 수·상품 구분 상태에 좌우된다. 예를 들어 **주문 500건 × 기본 확인 2초 + 그중 50건 × 추가 확인 20초**면 약 33분이다. 주문 수와 확인 속도 모두 가정이며 이름·상품 대조가 어렵다면 훨씬 길어진다. 상품 구간을 새로 나누고 가격을 적는 시간, 손님 연락처와 이름을 연결하는 시간도 별도다.

따라서 조건이 좋은 6,000장 시나리오의 일정 예산은 **초안 20~60분 + 검수·보완 30~60분 = 방송 후 약 50~120분**, 전체 영상 업로드 시간 별도다. 검수 30~60분 안에 상품·고객 대조까지 끝나는 조건을 검증해야 한다. 초기 시험이나 녹화 품질이 나쁘면 이 범위를 넘을 수 있다.

확정된 수백~수천 행을 단순 CSV/XLSX 파일로 저장하는 동작 자체는 수 초~1분 이내를 목표로 잡을 수 있다. 이 역시 구현 전 목표이며, 원본 영상 전송·OCR·검수·이미지 다량 삽입·고객별 PDF 대량 생성과 구분한다.

후속 개선으로는 녹화 중 이미 끝난 짧은 구간을 백그라운드에서 계속 처리할 수 있다. 처리 속도가 방송 진행을 따라가면 방송 종료 후 남은 연산 대기를 줄일 수 있다. 담당자가 실시간으로 주문을 입력할 필요는 없다. 별도 복잡도가 있으므로 첫 표본 시험과 방송 후 일괄 처리 검증 뒤 검토한다.

## 5. 구현 난이도와 개발 비용

다음은 경험 있는 개발자 1명, 화면 형태 1개, 한국어 중심, 표본과 요구사항 확보를 전제로 한 **누적 개발 일정 추정**이다. 이번 대화에서 시작한 작업이나 납기 약속이 아니다.

| 범위 | 난이도 | 누적 작업 기간 추정 |
| --- | --- | --- |
| 대표 녹화 구간의 OCR 비교·누락 및 시간 측정 | 중간 | 2~4 근무일 |
| 방송 한 회 처리, 반복 댓글 추적, 원본 대조 검수, 주문 초안 내보내기 | 중상 | 2~4주 |
| 오렌담마켓의 담당자 권한·처리 재개·고객 연결·비회원 주문장까지 연결 | 높음 | 4~8주 |

여러 기기의 임의 화면, 완전 자동 상품 추론, 별명이 같은 고객의 자동 식별, 결제대행사 변경·심사는 위 일정에 포함하지 않는다. 화면 녹화의 원본 누락은 개발 기간을 늘리는 것만으로 해결되지 않을 수 있다.

금전적인 개발비는 `필요 인일 × 합의한 일 단가 + 별도 인프라 비용`으로 산정한다. 외주 견적과 장비 구매 여부가 없으므로 확정 금액은 제시하지 않는다. 반복 운영에서는 OCR 호출료와 함께 **방송당 검수 인건비**를 따로 비교해야 한다.

프로젝트에는 별도 방송 주문 초안·검수 경로를 두는 안이 적합하다. 초기 영상 처리는 보조 담당자 PC 또는 별도 작업 프로세스에서 수행하고, 검토 가능한 결과를 오렌담마켓에 연결하는 방향이다. 기존 상품 등록·로그인·재고 검증을 전역으로 완화하지 않는다. 실제 고객 결제·플랫폼 수금·셀러 정산은 앞선 [개발 방향](../product-direction.md)의 별도 조건을 따른다.

## 6. 첫 검증의 범위와 판단 기준

필요한 표본은 **실제 녹화 20~30분 정도**다. 평상시뿐 아니라 20건이 몰리는 구간, 상품 전환, 동일 고객의 추가·변경·취소, 이름이 긴 고객을 포함한다. PC와 모바일 모두 가능하면 같은 방송의 짧은 구간을 양쪽에서 기록해 비교한다. 고객 정보가 포함된 표본을 외부 서비스로 보낼지는 시험 착수 때 정한다.

1. 사람이 원본에서 읽을 수 있는 주문 댓글을 기준 목록으로 만들고 기존 수기와 대조한다. 수기도 틀릴 수 있으므로 어느 쪽도 무조건 정답으로 취급하지 않는다.
2. 가능하면 주문 댓글 300~500건 이상을 모아 OCR 두 후보와 화면 선택 간격을 비교한다. 양이 부족하면 다른 구간을 추가한다. 튜닝에 쓰지 않은 구간에서도 확인한다.
3. 녹화 누락, 추출 누락, 잘못된 고객·상품, 중복 주문, 취소 처리 오류를 각각 세고, 자동 처리와 사람의 확인 시간을 잰다.
4. 20~30분 표본은 초기 탈락 요인 확인용이다. **3~4시간 전체 방송**에서 기록 지속성·장수·처리 시간·총 검수 시간을 다시 확인한 뒤 운영 여부를 판단한다.

성공 기준의 제안은 “화면에서 읽을 수 있는 주문 후보의 누락을 거의 없애면서, 잘못된 주문은 검수에서 찾을 수 있고, 최종 정리 시간이 기존보다 절반 이상 줄어드는가”다. 수치 목표를 정한다면 보이는 주문 후보 포착률 99% 이상 등을 **검증 목표**로 둘 수 있지만 달성 사실이나 미표시 주문까지 포함한 정확도로 홍보하지 않는다. 작은 표본에서 실수 0건이었다는 사실만으로 전체 방송의 무오류를 보장하지 않는다.

이 조건을 통과하지 못하면 녹화 방식·채팅 표시 영역을 개선하거나, 현재 수기 기록의 사후 전산화를 보조 자료로 결합한다. 최종 목적은 OCR 도입 자체가 아니라 방송을 지연시키지 않고 주문 정리 시간을 줄이는 것이다.
