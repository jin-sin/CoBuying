시험 시 반드시 기록할 증거: 테스트 프로젝트/빌드 버전, 시험 날짜·방송 ID, 운영자·보조 기기와 브라우저, 각 단계의 결과/소요 시간/실패 재시도, 고객 A/B 격리, 상품 한 개 약 20건의 입력 처리 시간, 중국 연길의 VPN 없는 iPhone·Android 일반 브라우저에서 첫 화면/청구/QR/캡처/송장 로딩 시간과 실패율. 실제 계좌 송금·실거래 없이 테스트 데이터로 먼저 진행한다.

테스트 Cloud 준비 자료는 [B02~B08 SQL 묶음](generated/test-cloud-b02-b08.sql), [증빙 버킷 정책](../../../supabase/storage/broadcast_evidence_bucket.sql), [수취 QR 버킷 정책](../../../supabase/storage/broadcast_receiver_qr_bucket.sql)이다. **2026-09-29 `orendam-broadcast-test` (`kshysvfxcjtixfveimai`)에 아래 1~5단계를 적용·조회 확인했다.** 후속 환경 재구성용 절차로 보존한다. 이후 실제 Auth JWT·QR/증빙 Storage와 고객 게이트웨이 HTTP 연속 흐름까지 확인했지만, 실제 화면의 30개 현장 시나리오는 아직 미실시다.

Cloud 사전검증: publishable key의 실제 HTTP에서 익명 고객 테이블·직원 workspace 접근 거절을 확인했다. 실제 두 Auth JWT에서 참여·20건 경합·회수와 Flutter 저장소 RPC가 통과했다. 별도 주문행·청구 스냅샷·private QR 파일 업로드/익명 다운로드 차단·무입금 발주 제외도 테스트 Cloud에서 통과했다. 고객 게이트웨이의 승인 쿠키·A/B 분리·증빙 업로드·복수 가상 입금·발주→부분출고를 한 테스트 데이터 흐름으로 통과했다. **같은 수취 건의 보완 증빙 경로와 실제 UI 클릭 경로는 이번 Cloud 연속 시험에 포함되지 않았다.** 이 자동 검증은 요구사항 §48의 실제 화면/현장 30단계를 대체하지 않는다.

1. SQL Editor에서 B02~B08 묶음 전체를 한 번 실행한다. 기존 B01 기준·B02 미적용 상태를 검사하며, 25개 증분 마이그레이션을 한 트랜잭션으로 적용한다. 오류가 나면 임의로 일부만 재실행하지 말고 오류를 기록한다.
2. Storage 화면에서 private 버킷 `broadcast-evidence`를 생성한다. 파일 제한 5 MiB, MIME `image/jpeg`, `image/png`, `image/webp`.
3. Storage 화면에서 private 버킷 `broadcast-receiver-qr`를 생성한다. 파일 제한 2 MiB, MIME `image/png`, `image/jpeg`.
4. SQL Editor에서 두 버킷 **정책** 파일을 각각 실행한다. 두 파일은 버킷 설정을 검사하고 RLS 정책만 추가하며 Storage 메타데이터 행을 직접 수정하지 않는다.
5. `broadcast_customer_devices`·`broadcast_invoices` 테이블과 두 private 버킷을 확인한다. 운영 프로젝트에는 적용하지 않는다. 게이트웨이의 service-role 키는 서버 환경변수에만 입력하고 채팅·저장소에 남기지 않는다.
