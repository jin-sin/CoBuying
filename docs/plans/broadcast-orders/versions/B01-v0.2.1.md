# B01-v0.2.1 · 로컬 HTTP·브라우저 검증

- 기록 시점: 2026-09-28T15:03:12+09:00. 상태: **진행 중**. 공통 문서 묶음: v2.2.0. 요구 기준: [판매자 요구사항 v1](../requirements-v1.md).
- 이전 단계 버전: [B01-v0.2.0](B01-v0.2.0.md). 제품 계약과 운영 DB는 바꾸지 않고 통합 검증 경로를 추가했다.

## 변경

- `tools/broadcast-tests/http.test.mjs`: 일회용 PostgreSQL 15·PostgREST 16.4를 127.0.0.1에서 실행해 기존 네 마이그레이션을 그대로 적용한다. 로컬 서명 JWT로 실제 HTTP RPC를 호출하고, 관리자·보조의 동시 주문과 권한 경계를 검사한다. `npm run test:http --prefix tools/broadcast-tests`로 실행한다. macOS Apple Silicon에서는 공식 PostgREST 릴리스를 SHA-256 확인 후 테스트 캐시에 받는다. 다른 환경은 `POSTGREST_BIN`을 지정한다.
- `build-restart-harness.sh`와 `restart_harness_main.dart`: 실제 방송 입력 페이지·기기 보관 코드를 별도 Flutter 웹 빌드에 넣어 응답 유실 → 브라우저 새로고침 → 같은 키 재확인을 수동 재현한다. 테스트 저장소는 가상 서버 응답만 제공하며 운영 서비스와 무관하다.

## 실제 검증

- 로컬 PostgreSQL 15.17 + PostgREST 16.4: 서명 JWT→HTTP→RPC 성공, 타 판매자·무인증 차단, 보조 코드 참여·회수 후 차단, 동일 키 동시 재시도 1행, 관리자·보조 두 JWT의 동시 20행/고유 순번, 고객·주문 페이지 조회 통과. DB/HTTP가 실제 두 프로세스·복수 연결이며 Supabase Auth 서비스에서 발급한 토큰은 아니다.
- 별도 Flutter 웹 빌드를 Chrome에서 조작: 주문 저장 후 응답 유실 표시와 신규 입력 잠금, 페이지 새로고침 후 미확인 요청 복구, 재확인 성공과 기록 정리 확인. 모의 저장소를 쓰므로 실제 HTTP 주문 영속성과 혼동하지 않는다.
- 기존 PGlite SQL 11건을 다시 실행했다. Flutter 위젯 7건·정적 분석·전체 앱 웹 빌드 결과는 [이전 기록](B01-v0.2.0.md)의 범위이며 이번 작업에서 제품 코드는 변경하지 않았다.

## 미검증·제한

- 실제 Supabase Auth 발급 JWT, 기존 운영 앱의 `SupabaseBroadcastRepository`를 거친 네트워크 호출, 두 실제 휴대폰, 보조 참여 링크의 로그인 리다이렉트와 회수 직후 화면 반응은 남았다. 로컬 HTTP 시험과 브라우저 재시작 시험은 각각 독립 하네스다.
- 운영 DB 적용·배포·실거래·고객 메시지 없음. 기존 미커밋 변경과 monitor-worker 보존. B02~B09 실제 기능은 별도 단계다.

## 다음 게이트

실제 테스트 Supabase Auth·PostgREST에 B01을 연결해 앱 경로를 두 기기에서 확인하고, 보조 참여 링크/회수와 재시작 후 동일 키 재확인을 끝까지 검증한다. [B01-v1.0.0 게이트](../stage-versions.md)를 모두 통과하기 전 완료로 표기하지 않는다.
