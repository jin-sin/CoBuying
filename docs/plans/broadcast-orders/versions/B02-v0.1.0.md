# B02-v0.1.0 · 고객 고정 링크 보안 경계 첫 구현

- 기록 시점: 2026-09-28. 상태: **진행 중**. 공통 문서 묶음 v2.2.0. B01은 [v0.2.4](B01-v0.2.4.md)로 진행 중이며 실환경 링크 검증을 이번 단계에서 억지로 완료 처리하지 않는다.

## 구현

- 증분 SQL `202609280004_broadcast_customer_access.sql`: 고객별 고정 locator, 새 기기 요청, 판매자 승인/회수, 30분 단회 활성화, 기기 세션과 고객 전용 조회. 고객/세션 비밀은 SHA-256 해시로 저장한다. 고객 URL만으로 주문·주소를 반환하지 않는다.
- `services/broadcast-customer-gateway/server.mjs`: 같은 출처 `/api/broadcast/v2/*`에서 요청 기기의 HttpOnly 쿠키와 활성 세션 쿠키를 검사한다. 브라우저에 service-role 키를 전달하지 않는다. POST Origin 검사, no-store/no-referrer, HTTPS Secure 쿠키. 활성화 응답이 유실돼도 같은 기기·토큰으로 재시도할 수 있다.
- 관리자 link/overview/approve/revoke는 기존 로그인 JWT RPC로 분리했다. 판매자가 기존 위챗 연락으로 확인하고 활성화 링크를 수동 전달하는 전제다.

## 검증

- PGlite: 타 판매자 링크 발급/승인 거부, URL만으로 비노출, 원래 요청 기기만 활성화, 토큰 재사용 거부, 다른 고객 locator 접근 차단, 회수 직후 차단.
- 로컬 게이트웨이 HTTP: 쿠키 없으면 백엔드 호출 전 401, 교차 출처 POST 403, pending 쿠키만으로 정보 비노출, 활성 세션으로만 A 고객 조회, B locator 거부.
- 일회용 PostgreSQL 15 + PostgREST: `service_role` JWT로 요청→승인→활성화→조회→회수 후 거부 통과. `npm run test:customer-access`와 `npm run test:http` 통과.

## 미구현·다음 단계

- 고객/관리자 실제 Flutter 화면, 한 줄 추가주문, 수정 요청·관리자 처리, 실서비스 HTTPS 프록시 배포와 중국 실기기 검증은 아직 없다. B02 완료가 아니다.
- SQL은 로컬 시험 DB에만 적용했다. Cloud 테스트/운영 Supabase에 B02 마이그레이션을 적용하거나 키를 저장소에 기록하지 않았다.
