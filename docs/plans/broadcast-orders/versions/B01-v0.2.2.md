# B01-v0.2.2 · 테스트 Supabase 준비와 앱 저장소 통합

- 기록 시점: 2026-09-28T15:43+09:00. 상태: **진행 중**. 공통 문서 묶음: v2.2.0. 이전 [B01-v0.2.1](B01-v0.2.1.md)은 변경하지 않는다.

## 변경

- 별도 Supabase Cloud 테스트 프로젝트에만 `tools/broadcast-tests/cloud_test_baseline.sql`의 최소 `seller_profiles`를 만든 뒤 기존 네 B01 마이그레이션을 순서대로 적용했다. 이는 운영 NAS의 Supabase가 아니다. 프로젝트 키·세션은 저장소에 넣지 않았다.
- `npm run test:adapter --prefix tools/broadcast-tests`를 추가했다. 일회용 로컬 PostgreSQL·PostgREST에 실제 `SupabaseBroadcastRepository`를 연결해 Flutter 앱 저장소의 조회, 주문 생성/동일 키 재시도, 타 사용자 거부를 검사한다. 기존 앱 전체 네이티브 훅과 분리해 실행한다.

## 실제 검증

- 테스트 프로젝트: Auth/REST 접속 성공. 적용 전 `broadcast_workspace` 미존재, 적용 후 익명 실행은 `42501` 거부. SQL Editor 조회에서 방송 테이블 8개, RPC 8개, 방송 테이블 RLS 모두 활성 확인. 기존 사용자 0명, 카카오 제공자는 비활성 상태.
- 로컬 `test:adapter` 통과. 이 검증의 JWT는 로컬 서명이며 Supabase Auth가 발급한 토큰이 아니다. 기존 `test:http`의 두 actor/20건 경합 검증도 이 실행에서 함께 통과했다.

## 미검증·다음 게이트

- 테스트 프로젝트에서 실제 Auth 사용자를 생성해 Auth 발급 JWT→Cloud RPC→앱 경로를 검증해야 한다. 카카오 로그인 제공자 설정 또는 격리 테스트용 로그인 경로가 필요하다. 실제 휴대폰 두 대, 참여 링크의 로그인 복귀/회수, 실제 앱 재시작은 남았다.
- 운영 DB 적용·배포·실거래·고객 메시지 없음. B02~B09 기능은 별도 단계. [B01-v1.0.0 게이트](../stage-versions.md) 전에는 완료로 표기하지 않는다.
