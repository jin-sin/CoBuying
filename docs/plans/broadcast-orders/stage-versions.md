# 방송판매 단계별 버전

현재 기준: 판매자 [요구사항 v1](requirements-v1.md), 공통 문서 묶음 **v2.2.0**. 기계가 읽는 현재 버전은 [version.json](version.json)이다. `B00`~`B09`는 개발 단계이며 버전 번호와 별개다. 사용자 P0는 모든 필수 기능을 포함한 시험 운영 목표다.

## 버전 규칙

- **공통 문서 묶음**: [계획](README.md), [화면·API](interfaces.md), [타입](contracts.d.ts), [화면 커버리지](ui-coverage.md), [동작 시안](../../prototypes/broadcast-orders/index.html)을 한 기준으로 다룬다. `v2.2.0`의 첫 숫자는 요구 흐름의 큰 교체, 둘째는 화면·상태·API 계약의 의미 있는 변경, 셋째는 의미를 바꾸지 않는 설명·검증 보완이다. 요구사항 v1 자체는 별도 문서이므로 수정할 때 변경 근거를 명시한다.
- **단계 버전**: `B01-v0.1.0`처럼 단계마다 독립적으로 붙인다. `v0.*`는 진행 중이며, 테스트가 일부 통과했어도 완료를 뜻하지 않는다. 단계 완료 기준을 모두 실제 코드에서 통과하고 미검증 항목을 처리했을 때만 `v1.0.0`으로 올린다. 이후 호환되지 않는 변경은 첫째, 기능·계약의 추가는 둘째, 설명·시험 보완은 셋째 숫자를 올린다.
- **한 번 기록한 버전은 고치지 않는다**: 새로운 단계 체크포인트마다 [작성 틀](versions/TEMPLATE.md)을 사용해 `versions/Bxx-vX.Y.Z.md`를 새로 쓰고 이전 기록은 보존한다. 현재 버전만 `version.json`과 아래 표에서 옮긴다. 같은 버전의 구현 범위·검증 결과를 소급 변경하지 않는다. 버전 문서는 그 시점의 결과·미검증·다음 게이트를 명시하고, 전체 MVP 완료로 해석하지 않는다.
- **동기화 단위**: 요구/화면/상태/API가 달라지면 계획·시안·API·타입·협업 지침을 같은 변경에서 맞춘다. 코드만 추가하고 계약이 그대로면 공통 버전을 억지로 올리지 않는다. 버전 증가와 근거는 [작업표](worklog.md)에 남긴다. 운영 배포·운영 DB 적용은 단계 완료와 별도로 기록한다.
- **Git 경계**: 현재 작업공간에는 기존 미커밋 변경이 있어 이 단계 버전은 문서 체크포인트이며 Git 릴리스/태그가 아니다. `v1.0.0` 완료 선언 시에는 해당 단계 파일의 검토 가능한 커밋과 재현 가능한 검증 기록을 연결한다. 무관한 변경을 태그에 함께 넣지 않는다.

단계 착수 시 `v0.1.0`을 만들고 이 표의 완료 게이트를 구체적인 검증 항목으로 풀어 쓴다. 앞 단계가 진행 중이어도 독립 개발은 가능하지만, 뒤 단계의 완료를 앞 단계의 미검증 해소로 간주하지 않는다. 공통 시안의 가상 성공과 실제 DB·HTTP 검증은 각 버전 기록에 구분한다.

## 체크포인트 작성 순서

1. 시작 전에 git 상태와 최신 작업표를 읽고 담당·수정 범위·시각을 기록한다.
2. 대상 단계의 이전 버전과 완료 게이트를 확인한다. 구현·계약 변경을 반영하고 필요한 고객/직원 예외를 검증한다.
3. 새 버전 기록에 **변경 / 실제 검증 / 미검증 / 다음 게이트 / 운영 반영 여부**를 적는다.
4. `version.json`·이 표·관련 문서 버전 표기를 함께 올리고 `npm run plan:check --prefix tools/broadcast-tests`를 실행한다. 버전 기록이 없는 숫자만 변경하지 않는다.
