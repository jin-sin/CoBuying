# 화면 커버리지 · v2.2.0

2026-09-28. B00 계획·화면 설계 인수인계표. **시안은 로컬 메모리 상태 체험이며 API·파일·인증·실제 입금 완료가 아니다.** 요구사항은 [v1](requirements-v1.md), 상세 API는 [interfaces](interfaces.md), 실제 구현 현황은 [worklog](worklog.md)를 우선한다.

## 구현 시 놓치면 안 되는 화면 상태

이 항목은 설계·수용 기준이다. 시안에서 서버 오류를 실제로 발생시킨 결과로 표시하지 않는다.

| 상태 | 표시 / 사용자의 다음 행동 | 검증 티켓 |
|---|---|---|
| 직원 저장 중 / 응답 유실 | 저장중 표시, 입력 유지, 같은 요청 다시 확인, 성공 확인 전 다음 저장 오인 금지 | B01 |
| 보조 담당자 참여·회수 | 관리자 일회용 30분 코드 생성/공유 → 기존 로그인 담당자 참여 → 관리자 접근 회수, 타인·만료 코드 차단 | B01 로컬 SQL/Flutter 연결, 실제 JWT/링크 검증 잔여 |
| 고객 최초 접근 / 세션 만료 | 주문·주소·청구 비노출, 기존 위챗 본인 확인 요청, 요청 기기만 활성화 | B02 |
| 처리중 수정 경합 | 최신 최종 내용 다시 표시, 판매자 재확인; 덮어쓰기 금지 | B02/B03 |
| 옵션 불명확 / 추가주문 마감 | 원문 확인대기, 담당자 확인; 마감 일시와 판매자 문의 안내 | B01/B02 |
| 청구 무효 / 새 판본 | 이전 송금안내 닫기, 새 청구/주소/최종 내용 확인 유도 | B03 |
| 선입금 잔액 충분 / 최종0원 | 주소·최종확인 후 완료, 추가 송금이나 캡처 요구하지 않음 | B03/B04 |
| 증빙 업로드 실패 | 파일/입력 유지, 재시도. 저장 완료 전 입금 확인 요청 금지 | B04 |
| 증빙 보완 | 고객에게 요청 사유·보완 제출, 기존 receipt에 파일 이력 추가, 금액 중복 금지 | B04 |
| 실제 수취 금액/통화 불일치 | 대조 예외로 보류, 실제 거래 확인·사유 기록, 변경된 잔액 고객 표시 | B04 |
| 환불 예정 / 완료 | 예정은 송금 완료가 아님, 실거래 확인 후 원장 반영, 수취와 환불 별도 표시 | B04 |
| XLSX 생성중 / 실패 / 만료 | 중복 클릭 방지, 동일 범위 재시도, 만료 재생성, 직원만 다운로드 | B05 |

| 청구 이후 새 추가주문 | 기존 청구에 몰래 추가하지 않고 새로운 미정산 행·별도 청구 | B02/B03 |

## 빠른 검토 순서

1. ‘320위안 업무 예시’ → 고객 주소/동의 → 300+20 복수 증빙 → 직원 실수취 확인 → 합산발주 → 부분입고/불량/부분출고.
2. 같은 예시에서 350위안 → 보완 요청/재제출 → 수취350 → 초과30 환불 예정/완료 → 순수취320 확인.
3. ‘새 기기 체험’ → 개인정보 비노출 → 요청 → 직원 처리할 일에서 기존 위챗 확인 → 고객 활성화.
4. 방송 회차 생성/전환 → 상품 비공개 등록/공개 → 기존 방송 주문과 분리 확인.
5. 고객·정산의 선입금 원장/관리자 주소 정정, 수취 설정, 내보내기 표의 개인정보 열 확인.
6. ‘15일 후 체험’으로 무입금/장기미송 확인. 320px 직원 입력과 390px 고객 페이지에서 횡스크롤 없이 조작 가능해야 한다.

실제 서버 구현자는 담당 티켓 완료 시 이 표와 작업표에 **어떤 환경에서 무엇을 검증했는지** 갱신한다. 시안 역할 전환, 가상 캡처 체크, XLSX 생성 완료 문구를 실제 보안·업로드·내보내기 성공 증거로 쓰지 않는다.
