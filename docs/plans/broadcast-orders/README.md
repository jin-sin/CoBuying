# 방송판매 MVP 개발 계획 v2.2.0

2026-09-23 · 기준: [판매자 요구사항 v1](requirements-v1.md). **실제 개발 착수**, 운영 배포 전. [단계별 버전과 완료 게이트](stage-versions.md), [현재 버전](version.json)을 함께 따른다. 이전 v1.4는 [보관본](archive/v1.4/README.md)이다. 현재 고객 직접 주문 중심 계획을 유지하라는 과거 지시는 폐기한다.

방송 중 더우인 채팅 → 직원 모바일 1회 입력 → 방송 후 고객 확인/추가/수정 요청 → 정산/입금 → 거래처 합산발주 → 입고/미송/교환 → 부분출고/송장. 제품 목표는 재입력 0회이며 방송 현장에서 사진은 필수가 아니다.

## 개발 구분

사용자 P0는 **첫 시험 운영에 필요한 전체 MVP**다. 작업 관리에는 B00~B09를 사용해 과거 P0 기반조사와 혼동하지 않는다. 일부 완료를 전체 P0 완료로 표시하지 않는다.

현재 공통 문서 버전은 `v2.2.0`, 진행 중인 B01의 현재 체크포인트는 [B01-v0.2.4](versions/B01-v0.2.4.md)이다. 공통 버전은 계획·화면/API·타입·시안의 기준을, 단계 버전은 실제 구현과 검증 상태를 나타낸다. B00 당시 문서의 정확한 스냅샷은 버전 체계 도입 전이라 소급 생성하지 않는다.

## 코드 구조

기존 Flutter/Supabase를 유지한다. `lib/features/broadcast_orders/`에 모델/저장소/운영 화면을 추가하고 `/seller/broadcast`는 `BROADCAST_ORDERS_ENABLED=true` 빌드에서만 연다. 기본 꺼짐. 일반 쇼핑몰 테이블·정산·재고·로그인은 변경하지 않는다. 신규 `supabase/migrations/*broadcast*.sql`만 추가하며 운영 schema.sql에 즉시 합치지 않는다.

직원 경로는 기존 Supabase JWT + 신규 판매자/구성원 권한 검사 + 원자적 RPC. 비회원 고객은 B02 같은 출처 게이트웨이 + HttpOnly 세션으로 별도 구현한다. 비회원에게 service key/JWT 관리 권한을 주지 않는다. 게이트웨이 런타임과 NAS 프록시는 B02 테스트 환경에서 결정하며 운영 인프라 변경은 별도다.

현재 시안은 `docs/prototypes/broadcast-orders`의 메모리 UI다. 실제 저장 경로는 Flutter/RPC이며 시안의 역할 전환·가짜 증빙은 인증/입금 구현이 아니다. 신규 B01 마이그레이션은 로컬 PostgreSQL 엔진 PGlite로 검증한다. PGlite 단일 연결 검증을 실제 NAS 다중 연결 경합 검증으로 표현하지 않는다.

## 개발 기본 결정 (판매자 확정 사항과 구분)

- **입력 속도:** 상품/옵션은 연속 입력 시 유지, 고객만 검색→선택→저장. 저장 후 고객 검색으로 초점 복귀. 20건에는 이만큼의 입력 시간이 여전히 필요하므로 ‘방송을 안 기다림’은 현장 파일럿 성공 조건이다. 다음 소개로 넘어가도 직전 상품에 계속 입력 가능. 단순 기계 저장 속도를 현장 성공으로 판단하지 않는다.
- **목록:** 고객 닉네임은 서버 부분검색·중복 닉네임 ID 구분·키셋 더 보기. 주문 기록도 회차별 원순번 역순 페이지를 사용한다. 초기 workspace에 고객/주문 전체를 싣지 않고 상품의 접수 이력 여부는 서버가 계산한다. 페이지에 보이는 건수는 방송의 총 접수 건수가 아니다.
- **재시도:** 사용자 저장 동작마다 UUID, 같은 동작 재시도만 같은 키. 동일 옵션을 다시 주문하면 새 UUID/새 행. 네트워크 오류 시 입력 내용과 키 보존. 앱 재시작에도 계정·판매자별 미확인 명령을 기기에 보관하고 먼저 같은 키로 재확인한다. 보관 실패 시 전송하지 않으며 서버 확정 뒤 기록을 지운다. 서버 성공만 접수로 표시한다. 닉네임 중복 허용, 위챗 관리 정보로 식별, 내부 ID로 저장.
- **순서:** 서버 sequence/created_at 불변. 직원이 뒤늦게 입력한 채팅의 실제 순서와 저장 순서가 다를 수 있다. MVP 기본은 접수 저장 순서이며 채팅 시각은 참고로 보존 가능. 임의 소급 순번 조작은 하지 않는다. 시험에서 누락/대기열이 발견되면 별도 수신 큐 개선으로 기록한다.
- **금액:** 상품 기준 단가는 KRW 정수. 환율은 `1 CNY = X KRW` (소수4자리까지), 청구 판본에 고정. KRW 원·CNY 분 단위 정수, 총액 변환은 마지막에 반올림. 한국 배송비 KRW/중국 배송비 CNY를 각각 원래 통화로 보존하고 청구 기준으로 환산. 반올림 차액은 내부 기록. 양 통화는 선택 대안이지 더할 금액이 아니다.
- **선입금:** 고객 원장 잔액과 청구 배분을 분리. 실제 수취 확인된 금액만 한 번 차감. 청구액을 초과한 잔액은 유지, 최종 입금액 음수 금지. 취소 시 차감 배분을 되돌리고 이력 보존. 선입금 자체는 상품 주문 전체의 ‘입금완료’가 아니다.
- **송금:** 한 청구서의 결제 통화를 고객이 선택. 첫 증빙/수취 시작 후 통화를 고정하고 같은 통화의 추가 입금 지원. 혼합 통화 송금은 임의 환산 완료 대신 예외 처리함으로 보낸다. 대리 송금 허용, 수취 계정+거래 ID 중복 사용 금지. 합계/부족/초과/환불대기를 별도 계산.
- **입금 전 수정:** 미입금 원본 행을 담당자가 정정할 수 있지만 원본과 변경 기록 보존. 발행 청구는 수정 시 새 판본, 고객은 최종판과 ‘변경됨’을 확인. 수취 확인 전이라도 증빙 제출/송금 신고가 있으면 대조가 끝날 때까지 수정 보류. 일부 실제 입금도 수정·취소 잠금. 단순 선입금 보유와 구분. 입금 후 판매 변경/취소 기능은 제공하지 않지만 품절/초과금/불량 등 사후 예외와 실제 환불 기록은 별도 관리한다.
- **주소:** 정산서 발행 후 수집. 신규는 배송국가(KR/CN)만 먼저 선택해 배송비 산정하고 전체 주소는 발행 후 입력. 국가 변경/택포 조건 영향 시 미입금 청구 재발행·송금 잠금. 출고 시 주소 스냅샷. 이미 나간 출고 주소는 수정하지 않는다.
- **추가 주문:** 상품+한 줄 원문 우선 저장, 애매한 옵션/수량은 확인 대기로 표시. 추측 자동 확정 금지. 확정된 기존 청구/발주에 몰래 더하지 않고 새 미정산 행으로 기록한다. 기존 청구 입금 후 추가 건은 별도 청구로 진행.
- **상품 수정:** 접수 전 정정 가능. 공개 상품을 정정하면 비공개로 돌아가며 다시 확인·공개한다. 접수 이력 이후 상품 자체 정정과 고객 주문 정정을 분리, 주문 스냅샷 자동 덮어쓰기 금지. 소프트삭제/복구에도 상품 번호 재사용 금지. 현재 코디는 공개 상품만 복수 선택.
- **기한:** 회차 기본3일(변경 가능). 미입금은 청구 발행+72시간, 장기미송은 해당 발주+14일 **초과**. 부분입금/확인대기를 자동 취소 후보와 섞지 않는다. 일정 지연은 관리 작업으로 남고 자동 취소 없음.
- **수량:** 원 주문행 → 청구행 → 발주배분 → 입고배분 → 출고행을 ID로 연결. 정상입고+불량교환+미송+출고 수량을 중복 계산하지 않는다. 부분입고/출고는 수량을 갖는 사건이며 라인당 단일 status만으로 표현하지 않는다. 서로 다른 거래처·상품·옵션을 합치지 않는다.
- **고정 링크:** 고정 비밀 URL만으로 전 정보 접근 허용하지 않는다. 고객별 고정 공개 식별 URL+등록 기기 세션. 새 기기 최초 접근은 판매자가 기존 위챗 연락 경로로 본인 확인 후 일회용 활성화 링크를 전달. 이후 고정 URL 반복 사용. 만료/분실은 같은 경로 복구. 비밀번호/가입은 없다. URL만 넘겨받은 다른 사람에게 개인정보가 보이지 않는 것이 수용 기준이다.

## 검증 / 범위

[화면·상태·API](interfaces.md), [타입](contracts.d.ts), [작업표](worklog.md)를 함께 갱신한다. v1의 30개 시나리오는 B09에서 실증한다. 테스트 계획에는 판매자A/B/보조/무로그인 권한, ID 바꿔치기, 같은 요청 재전송, 동시 수정·첫 수취, 중복 수취·선입금, 발주 중복, 과입고·불량 과출고, 주소 스냅샷, 320px와 실기기 입력을 포함한다.

DB 구현 참고: [Supabase 함수 권한](https://supabase.com/docs/guides/database/functions), [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [로컬 PGlite 검증](https://pglite.dev/docs/). 공개 함수의 기본 실행 권한을 명시적으로 회수한다.

## 2026-09-28 화면 상세 보완 (B00)

[화면별 커버리지](ui-coverage.md)에서 직원/고객 진입 경로와 실제 구현 단계를 함께 확인한다. 이번 작업은 남은 계획과 인터페이스를 마무리한 것이며 B01의 실제 Flutter/SQL은 수정하지 않았다. B02~B09 완료나 실제 고객 시험 성공을 뜻하지 않는다.

- 방송별 선택/날짜/준비·접수·마감, 상품 공개 순서, 고객은 선택 방송 카탈로그와 자신의 전체 주문 이력을 본다. 청구는 선택 방송의 미정산 행만 포함한다. 발주/미송 처리함은 전체 방송의 미처리 업무를 모은다.
- 수취 안내는 확인된 수금 방법만 새 청구에 스냅샷으로 포함. 안내 변경으로 이미 보낸 정산서의 예금주·QR을 덮어쓰지 않는다. 고객이 통화와 수취 방법을 선택한다. 추가 송금은 같은 통화를 유지하되 청구에 포함된 다른 수취 방법을 선택할 수 있다.
- 증빙 보완은 같은 입금 건에 파일 이력을 추가한다. 입금액을 새로 더하지 않는다. 보완 중에도 송금 잠금과 처리할 일이 유지된다.
- 초과금은 환불 예정→판매자가 실제 송금→거래번호 대조 후 완료. 확인수취·환불누계·순수취를 분리, 이미 예정/완료한 금액을 중복 예약하지 않는다. 고객 주문 변경/취소와 별도인 초과금 반환이다.
- 선입금 원장은 실수취/청구 배분/배분 반환을 분리한다. 선입금으로 최종 청구액이 0이 된 경우에도 주소 입력과 최종 내용 확인 후에만 발주 대상이 된다. 과거 선입금 잔액만으로 자동 완료시키지 않는다.
- 관리자 주소 정정은 고객 요청 사유를 남기고 미래 출고에 적용한다. 미입금 상태에서 국가가 바뀌면 영향을 받는 청구를 무효화·선입금 반환 후 재발행한다. 입금 후 국가 변경은 배송비 예외 검토로 보류하고 일반 주소 정정 화면에서 즉시 적용하지 않는다. 이미 출고한 주소 불변.
- 고정 링크의 새 기기 화면→본인 확인 요청→직원이 기존 위챗으로 확인→일회용 링크 활성화→개인 페이지. 분실 시 기기 접근 회수. 시안 역할 전환은 실제 권한 설계의 대체가 아니다.
- 내보내기는 표 선택→거래처 범위→열/수량 미리보기→개인정보 범위 확인→생성 완료/실패 상태로 설계한다. 시안은 미리보기·생성 완료 체험까지만 제공한다. 실제 XLSX 저장·다운로드·만료는 B05에서 구현한다.

방송 날짜+기한의 개발 기본안은 `Asia/Seoul` 방송 당일 00시 + 집중 관리 일수다. 고객에게는 명시적 마감 일시를 표시한다. 이전 B01 생성 시점+일수 동작은 잔여 개발에서 교체한다. 기존 청구 금액은 회차 설정 변경과 독립한다.
