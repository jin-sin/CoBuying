# 방송 주문 구현 계획 v1.4

서비스명은 **오렌담마켓 / ORENDAM**(축약명: 오렌담)이다. 모의 UI의 판매자는 ‘샘플옷장’이며 플랫폼과 실제 수취 주체를 구분한다. 서비스 표시명 변경은 [브랜드 기준](../../brand.md)을 따른다. 주문 정책과 API 계약은 v1.4를 유지한다.

작성: 2026-09-13 · 상태: **설계 및 모의 화면 작성 / 실제 기능 미구현**

목표는 더우인에서 방송을 보던 고객이 회원가입 없이 오렌담마켓에 구매 요청을 남기고, 방송 후 자신의 청구서와 송금 확인 결과를 보는 것이다. 담당자는 현장에서 상품을 한 번씩 등록하고 방송 후 확보 수량·청구·입금을 관리한다. 주문이 20건 들어와도 고객별 타이핑을 기다리지 않는다.

이 문서가 현재 구현 기준이다. 대화 과정의 다른 후보는 [개발 방향 기록](../../product-direction.md)에 보존한다. [화면·API 규약](interfaces.md), [타입 계약](contracts.d.ts), [작업표](worklog.md), [클릭 가능한 시안](../../prototypes/broadcast-orders/index.html)을 함께 읽는다.

## 1. 고객과 운영자가 실제로 하는 일

| 시점 | 방송 진행자·보조 담당자 | 고객 |
|---|---|---|
| 방송 전 | 셀러 고정 링크를 기존 연락 경로로 공유. 빈 방송 회차 생성 | 일반 브라우저에서 링크를 열어 두거나 저장 |
| 현장 소개 | 짧은 이름·가격만 등록, 번호는 자동 부여. 방송에서 번호를 함께 안내 | 더우인에서 시청 |
| 주문 시간 | 상품 몇 개 소개 후 새 소개를 잠시 멈춤 | 오렌담마켓 상품 목록에서 옵션·수량 선택, 구매 요청 저장, 직접 더우인 복귀 |
| 방송 종료 | 요청을 마감하고 공급 가능 수량 확인 | 자신의 요청 확인, 중국 배송지 입력 |
| 청구 | 수량·가격·배송비 확인 후 고객별 청구서 발행 | 변경 사항과 최종 금액 확인 후 송금 안내 열기 |
| 송금 후 | 실제 수취 계정 거래 내역과 증빙 대조 | 해당 거래 캡처 첨부 → 입금 확인 요청 |
| 입금·배송 | 수금 확인 권한자가 입금 확정, 담당자가 배송 정보 등록 | 확인 대기/완료·배송 조회. 가입은 선택 |

**‘다음 상품’ 버튼으로 고객 장바구니의 대상을 바꾸지 않는다.** 상품은 고유 번호와 짧은 이름으로 고정되어 목록에 남는다. 사진 촬영·첨부를 현장 업무에 포함하지 않는다. 소개 중인 상품 표시는 보조 정보일 뿐이다. 주문 시간 종료와 구매 요청 마감도 다르다. 3~5개 소개 및 60~90초 휴식은 파일럿 가정이며 고정 운영 규칙이 아니다.

## 2. 확정된 요구와 설계 기본값

확인된 조건: 더우인 방송 3~4시간, 현장 상품 사전 파악 불가, 보조 담당자 PC/휴대폰 사용 가능, 상품당 최대 20건 주문, 방송 후 취합 가능, 한국어 중심, 중국 주소 배송, VPN 없는 중국 일반 브라우저, 강제 가입 없음. 위챗 송금 수취인은 아내(셀러) 개인 계정이며 알리페이도 사용하지만 명의·계정 유형은 아직 미확인이다.

이번 설계 기본값:
- 한 구매 요청은 **한 손님 × 한 셀러 × 한 방송 회차**, 한 청구서는 한 통화다. 여러 방송/셀러의 합산 결제는 후속 범위다.
- 회차 기본 예시는 CNY, 금액은 분(1/100위안) 단위 정수로 저장한다. 실제 운영 통화는 회차 게시 전 선택·고정한다. 기존 원화 금액과 더하지 않는다.
- 임시 구매 요청은 재고 확보나 확정 판매가 아니다. 공급 확정 전 송금 안내를 열지 않는다.
- 상품 가격을 모르면 초안으로 저장할 수 있으나 고객에게 주문 가능으로 게시하려면 이름·가격이 필요하다. 색상·사이즈 목록은 선택 입력이다. 목록을 생략하면 손님이 원하는 옵션을 짧게 직접 적고, 선택 사항도 생략하면 방송에서 소개한 기본 옵션으로 요청한다. 직접 적은 옵션은 확정 재고가 아니며 방송 후 담당자가 공급 여부를 확인한다. 사진이 없는 빈 썸네일이나 대체 상품 그림을 쓰지 않고 번호·이름·가격으로 표시한다.
- 초기에 위챗페이·알리페이는 **기존 송금 경로 안내 + 수동 수취 확인**이다. PG 결제 버튼이나 자동 승인으로 표현하지 않는다. 확인된 수취 설정만 노출한다.
- 고객이 청구 내용에 동의한 버전만 송금 대상으로 사용한다. 발행 후 금액 수정은 새 버전이며 재확인이 필요하다.

### 현장 상품 수정·삭제 (사용자 피드백 반영)

- **아직 구매 요청 접수 이력 없음:** 이름·가격·옵션을 수정하거나 삭제할 수 있다. 고객이 담아둔 초안이 있을 수 있으므로 ‘접수 0건’을 ‘아무도 보지 않은 상품’으로 취급하지 않는다. 삭제는 고객 목록에서 숨기는 처리이며 담당자는 복구할 수 있다. 복구는 판매 중지 상태로 돌려 내용을 확인한 뒤 재개한다.
- **구매 요청 접수 이력 1건 이상:** 이름·가격·옵션 및 옵션 메모 허용 여부를 모두 고정한다. 오타도 일반 상품 수정으로 덮어쓰지 않는다. 담당자 화면은 수정 비활성·사유 표시, 서버도 직접 호출을 거부한다. 삭제 대신 판매 중지/재개로 접수 가능 여부만 바꾼다. 취소된 요청도 이력이며 전부 취소되어도 잠금을 풀지 않는다. v1.1의 ‘접수 후 이름·가격 수정 허용’은 폐기한다.
- **접수 후 정정 필요:** 먼저 판매 중지한다. 금액 정정은 고객별 정정 이유와 이전/정정 금액을 표시한 청구서로 명시적 동의를 받는다. 이미 발행한 미송금 청구서는 새 버전으로 재발행한다. 다른 실제 상품으로 바뀌는 경우 새 ID·번호로 등록하고 고객이 별도 요청하게 하며 기존 요청을 몰래 옮기지 않는다. 기존 요청 취소도 고객 확인과 이력을 남긴다. 정정에 동의하지 않은 건은 수정된 내용으로 확정·송금 안내하지 않는다.
- **이미 청구·송금된 건:** 판매 중지가 기존 청구서·입금·배송을 취소하지 않는다. 수취 확인 중에는 청구 금액을 잠그고, 수취 완료 뒤 정정은 예외/환불 절차를 따른다. 이미 수취한 금액을 상품 수정으로 바꾸지 않는다.
- 상품 번호는 회차 안에서 단조 증가하고 삭제해도 재사용하거나 목록 순서에 맞춰 재번호를 붙이지 않는다. 서버 상품 ID와 번호·수정 이력을 유지한다.
- **담기만 한 상품의 변경:** 기존 선택을 자동으로 새 가격에 맞추지 않는다. 이름·개당 가격·옵션의 변경 전후를 보여주고 ‘변경 내용 확인’에서 현재 옵션을 재선택하거나 상품을 빼도록 한다. 확인 전 요청 저장을 막고, 확인 후에도 최종 저장 시 서버가 버전·판매 상태를 다시 검사한다. 새 정보 확인은 담기의 갱신이며 요청 접수 성공과 구분한다.
- 방송에서 웹으로 돌아왔을 때와 요청 화면 진입 시 최신 정보를 조회한다. 모든 화면이 같은 순간에 갱신된다고 보장하지 않으며, 통신 오류에는 로컬 초안을 보존하고 성공으로 표시하지 않는다. 이미 저장된 요청의 유지/수량 감소는 허용하되 신규·증가·옵션 변경은 최신 정보 검사를 거친다.
- 상품 수정과 첫 구매 요청 저장은 서버에서 같은 상품 잠금 아래 검사·처리한다. 수정이 먼저면 구버전 요청을 거절하고, 요청이 먼저면 상품 수정을 거절한다. 삭제·접수 마감 경합도 같은 순서로 처리한다.
- 현재 시안에서 변경 전후 확인, 접수 후 수정 잠금, 삭제/복구·판매 중지와 기존 요청 보존을 체험한다. 정정 청구 작성·변경 전후 안내·고객 동의/수정 요청·재발행, 상품별 제외 요청과 담당자 반영, 전체 제외 요청 후 미송금 주문 취소는 v1.4 시안에서 이어서 체험한다. 실제 서버 권한·경합·영구 감사 기록은 후속 구현한다.

### 상품을 빼고 싶다는 고객 요청

고객이 상품·옵션별 ‘이 상품 제외 요청’에서 대상과 미송금 여부를 확인한다. 청구 권한자가 해당 항목을 제외하고 남은 상품 기준으로 배송비를 재확인해 새 청구서를 발행한다. 고객은 제외 내역과 새 합계를 확인해 다시 동의한다. 요청만으로 금액을 바꾸거나 원 주문을 삭제하지 않는다.

현재 청구의 모든 상품을 제외하도록 고객이 확인했다면 담당자가 전체 주문 취소를 확인한다. 주문 cancelled와 청구 void를 함께 기록하고 0원 청구서는 만들지 않는다. 일부 제외 요청을 전체 취소로 확대하지 않는다. 이미 송금/증빙 확인이 진행된 건은 미송금 취소 경로에서 처리하지 않는다. 원 요청·과거 청구·상품 접수 이력은 보존한다.

## 3. 프로젝트에 붙이는 위치

같은 프로젝트에 독립된 `broadcast_orders` 기능으로 추가한다. Flutter 테마·판매자 계정·권한 검증 기반을 재사용하되, 기존 `orders`, `order_items`, `cart_items`, `create_order`, 정산 뷰에 방송 요청을 직접 넣지 않는다.

| 경계 | 후속 구현 위치 / 책임 |
|---|---|
| 고객·담당자 화면 | `lib/features/broadcast_orders/` — 모델, 저장소 인터페이스, Riverpod 상태, 고객/운영 화면. 우선 웹 파일럿 |
| 라우트 | `lib/router/app_router.dart` — 공개 `/s/:slug/live`, 개인 `/broadcast/me/:requestId`, 복구 `/broadcast/recover`; 운영 `/seller/broadcasts/...` |
| 같은 출처의 API | `/api/broadcast/v1/` → 새 서버 게이트웨이. 브라우저는 비회원용 HttpOnly 쿠키, 담당자는 기존 Supabase JWT 사용 |
| 서버 코드 | `supabase/functions/broadcast-api/` 후보 — 기존 NAS의 Edge Runtime 작동을 P0에서 확인한 뒤 사용. 안 되면 독립 서버 컨테이너 결정과 비용을 기록하고 계약은 유지 |
| DB | 신규 버전별 마이그레이션과 `broadcast_*` 테이블·트랜잭션 함수. 기존 `schema.sql`에 즉시 덧붙여 운영 적용하지 않음 |
| 파일 | 신규 비공개 `broadcast-evidence` 버킷. 공개 `product-images`에 송금 내역을 넣지 않음 |
| 인프라 | `tools/nginx.conf`의 공유 경로와 API 프록시를 별도 변경. 해시 라우팅과 POST 보존을 시험 |

시안은 프레임워크에 종속되지 않는 HTML/CSS/JS로 문서 폴더에 둔다. 후속 실제 UI는 위 Flutter 구조로 옮긴다. 시안의 메모리 상태·데모 손님 전환·가짜 증빙을 실제 인증·저장 코드로 재사용하지 않는다. 중국 회선에서 Flutter 초기 구동이 파일럿 기준을 충족하지 못하면 공개 고객 화면을 가벼운 웹으로 분리하는 결정을 P6에서 기록한다. 지금 두 고객 앱을 동시에 만들지 않는다.

서버 게이트웨이는 **새로 필요한 구성**이다. 현재 정적 nginx와 클라이언트 Supabase 호출만으로 HttpOnly 비회원 세션이 구현되었다고 가정하지 않는다. 서비스 키는 서버에만 두며 모든 요청의 guest/seller 범위를 검증하고 원자적 DB 작업만 호출한다. 서비스 키는 RLS 우회 가능하므로 RLS만을 유일한 방어로 삼지 않는다.

| Invoice / InvoiceLine | 변경 불가한 발행 버전, 확정 수량·단가·배송비·총액·수취 설정 스냅샷·동의 시각 |
| PaymentEvidence / PaymentSubmission | 비공개 객체·검증 상태, 청구서 버전, 선택 수단, 제출 이력·추가 확인 사유 |
| Receipt / PaymentReview | 수취인, 실제 수취액·통화·시각·거래 식별자, 대조한 확인자·결정·사유 |
| Shipment / AuditEvent | 배송 회사·송장·이력, 주요 변경의 행위자·시각·전후 버전 |

상태는 서로 다른 축으로 유지한다.
- 방송: `draft → open → closed → archived`. 소개/주문 시간 표시는 open 안의 안내다.
- 요청: `submitted → locked → invoiced` 또는 `cancelled`. 마감 전 수정/취소 가능, 청구 후 임의 요청 변경 불가.
- 청구서: `issued → accepted → settled`. 고객이 미송금을 확인하고 수정 요청을 남기면 `change_requested`로 바뀌며 송금 안내를 닫는다. 재발행은 새 판본으로 `issued`, 이전 청구는 `superseded`로 보존한다. 고객 거절은 자동 주문 취소가 아니다. accepted 청구는 직접 정정을 잠그고 미송금 확인을 포함한 고객 수정 요청 후에만 새로 발행한다.
- 입금: `unpaid → pending_review → confirmed` 또는 `needs_info → pending_review`. `pending_review` 동안 청구서 금액 변경·중복 제출을 막는다.
- 배송: `not_ready → preparing → shipped → delivered`. confirmed 이전에는 출고 불가.

부분 공급은 청구서에 원래 요청 수량과 확정 수량을 같이 보여 고객이 동의한다. 부족/초과 송금은 `needs_info`로 보류하며 임의로 전체 입금 완료 처리하지 않는다. MVP는 한 청구서에 한 번의 정확한 금액 수취를 원칙으로 한다. 예외 송금·환불은 운영자가 실제 거래를 확인해 별도 기록하고 사유·금액·상태를 남긴다. 환불 완료 전 ‘환불 완료’ 표시는 금지한다. 자동 환불·분할 결제·여러 청구서 합산 배분은 후속 범위다.

## 5. 회원가입 없는 접근과 증빙

공용 링크는 목록만 공유하고 비밀 값을 담지 않는다. 최초 쓰기 전 서버가 256비트 무작위 접근 자격을 발급해 Secure/HttpOnly/SameSite=Lax 쿠키로 관리한다. 서버 토큰 해시, 7일 유휴·30일 절대 만료를 설계 기본값으로 둔다. 변경 API는 Origin 및 CSRF 토큰을 검사한다. 같은 기기의 다른 사람은 ‘다른 손님으로 시작’을 통해 이전 자격을 종료한다. 손님 ID를 body로 받아 다른 사람의 주문에 쓰는 API를 만들지 않는다.

같은 브라우저에서는 내 주문을 이어서 연다. 다른 브라우저/만료 시에는 판매자가 기존 확인된 연락 경로로 **주문 하나에만 유효한 일회용 복구 링크**를 전달한다. 복구 링크는 24시간 유효하고 새 발급 시 이전 링크를 폐기한다. 링크 열기만으로 소비하지 않고 명시적 ‘내 주문 연결’ POST에서 소모한다. 비밀은 URL fragment에서 한 번 읽고 주소에서 지우며 분석·접속 로그에 남기지 않는다. 복구된 자격은 해당 주문 범위만 가진다. 전체 주소·증빙 재열람과 결제 후 배송지 변경에는 추가 확인 절차를 거친다. 닉네임만 대면 복구해 주지 않는다. 과거 제안의 개인 링크 저장을 영구 비밀번호처럼 사용하는 방식은 채택하지 않는다.

증빙은 JPEG/PNG/WebP, 최대 3장·장당 8MB를 초안 제한으로 둔다. 업로드 예약 → 서버가 실제 크기·형식·소유권 검사 → 저장 완료 → 제출 순서다. MIME 헤더만 신뢰하지 않고 디코딩 가능한 이미지인지 검사한다. 캡처의 금액·통화·수취인·시각·완료 여부가 읽혀야 하며 다른 잔액/거래 노출을 요구하지 않는다. 업로드 실패 시 선택 내용과 재시도 동선을 보존한다. 파일 하나가 이미 다른 제출에 사용됐으면 조사 대상으로 표시하되 해시 일치만으로 사기를 확정하지 않는다.

고객 캡처는 대조 자료다. 수금 확인자는 실제 수취 계정의 내역을 별도로 보고 거래 식별자·금액·수취인·시간을 기록한 후 확정한다. 확인된 거래 식별자 재사용은 DB에서 막는다. 확인자는 실제 수취액이 청구 금액과 같아야 confirmed로 바꿀 수 있다. 이미지 첨부가 불가능한 경우 거래 정보와 사유를 남기는 ‘첨부가 어려워요’ 경로로 담당자 확인을 요청할 수 있지만 자동 완료는 동일하게 금지한다.

비회원 접근과 쿠키 선택은 [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)을 참고했다. 비공개 파일 접근은 [Supabase Storage 권한 문서](https://supabase.com/docs/guides/storage/security/access-control)를 참고했다. 구체 만료·용량 값은 이 프로젝트의 설계 기본값이며 공급자 규정이나 법정 보존 기간이 아니다. 보존·삭제 기간은 파일럿 전 운영 정책으로 정하고 만료 후 원본·백업 삭제 절차까지 확인한다.

## 6. 수금과 기존 중개 정산 연결

MVP 수금 주체는 `seller_direct`만 활성화한다. 위챗과 알리페이는 각각 실제 수취 명의 확인·송금 방법 시험 후 활성화한다. 알리페이 수취 명의가 미확인인 현재는 실제 서비스에 노출할 수 없다. 시안의 두 수단은 가상 설정이다.

새 `Receipt`를 기존 `seller_settlements`의 판매대금으로 삽입하지 않는다. 방송 주문 통계에는 직접 수금액과 플랫폼 지급액을 구분해 표시하고 직접 수금의 플랫폼 지급액은 0으로 유지한다. 플랫폼 수수료 청구는 약정과 통화별 처리가 정해진 이후 별도 채권으로 연결한다. PG 기반 플랫폼 수금은 사업 구조 심사·계약·한 기기 결제 시험을 마친 뒤 별도 단계에서 추가한다. 토스 교체나 KG이니시스 가입은 이번 계획의 선행 조건이 아니다.

## 8. 파일럿 기준과 남은 확인

아래 수치는 측정 목표이며 현재 성능 결과가 아니다.
- 연길 실제 고객 iPhone Safari와 Android 일반 브라우저, 최소 통신망 2개, VPN 없이 실행. 첫 목록 사용 가능 p95 5초 이내, 요청 저장 p95 3초 이내를 목표로 각각 30회 이상 측정하고 실패율과 표본 수를 같이 기록한다.
- 동시 20명 저장 3회에서 요청 유실/중복 0건. 네트워크를 끊은 뒤 재시도해 서버 결과와 고객 상태가 일치하는지 별도 확인한다. 접수 실패는 성공 표시하지 않는다.
- 상품 등록 시간·주문 구간 완료율·고객의 외부 앱 전환 횟수·담당자 방송 후 정리 시간을 측정한다. 목표는 기존 수기 소요와 비교해 개선 여부를 확인하는 것이다.
- 위챗/알리페이 각각 휴대폰 한 대로 송금 → 캡처 → 브라우저 복귀 → 첨부를 시험한다. QR 앨범 인식, 앱 자동 실행, 더우인 자동 복귀를 가정하지 않는다.
- NAS 운영 문서에 02:00~08:00 정지가 기록되어 있다. 야간 주문/증빙 수신이 필요하면 운영 시간 조정 또는 항상 켜진 수신 구성을 결정해야 한다. 현재 인프라로 24시간 접수를 약속하지 않는다. 점검 중 입력 손실·거짓 성공 표시를 막고 재시도를 안내한다.
- 신규 시청자에게 전달 가능한 더우인 계정 내 공식 진입 경로는 미확인이다. 기존 고객 사전 링크 공유로 먼저 시험하고, 마스킹 우회에 의존하지 않는다.
- 상품 품목·가격/배송비 정책, 알리페이 수취 설정, 증빙 보존 기간·담당자 범위는 실제 사용 전 확인한다. 이것들이 시안 작성이나 독립적인 개발을 막는 사유는 아니다.
